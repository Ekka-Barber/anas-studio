# SITE-STATE-1: the site's state, switched from the admin

Contract for one side package (D46, D47). Owner, 2026-10-02: "now build the maintenance page, do the same three designs idea, make sure all get activated from admin dashboard (settings ..) check the best place there".

## What exists already (outside the product, live)

`artifacts/soon/` (its README): three soon designs (`site/v/<letter>/`) and three maintenance designs (`site/m/<letter>/`), served by the Worker `anas-studio-soon` on anas.studio. `worker.js` shows one design at random per load, never the same twice in a row; maintenance answers 503 with `Retry-After`. The state is the Worker variable `MODE` (`soon` or `maintenance`), switched today by a deploy: `node --env-file=.env artifacts/soon/deploy.cjs --mode=maintenance`. Proven on the live domain on 2026-10-02 (on: 503 and the maintenance title; off: 200 and the soon title). `https://anas.studio/m/` shows a maintenance design without switching anything.

## What this package adds

The owner switches the state in the admin, and the domain follows it within half a minute, with no deploy.

Three states, one stored word:

| State | Stored | A visitor sees |
|---|---|---|
| «مفتوح» | `open` | the site |
| «قريباً» | `soon` | a soon design, 200 |
| «صيانة» | `maintenance` | a maintenance design, 503 |

### Where in the admin

`/admin/settings` («الإعدادات», owner only), as its first section, «حالة الموقع», above «إعدادات الموقع». It is the one control there that changes what every visitor sees, so it comes first. It is built like the «الشراء» switch in `CommerceSettingsForm.tsx`: the `switchBox` fieldset, the `admin` function, a fresh TOTP through `StepUp`, the state read back after the change.

Words (the owner approves them before acceptance):
- the current state as a sentence: «الموقع الآن: مفتوح» / «الموقع الآن: قريباً» / «الموقع الآن: صيانة»;
- under it: «مفتوح: يرى الزائر الموقع كاملاً.» · «قريباً: يرى الزائر صفحة «قريباً» بدل الموقع.» · «صيانة: يرى الزائر صفحة الصيانة إلى أن تفتح الموقع.» · «لوحة التحكم تعمل في كل الحالات.» · «يظهر التغيير للزوار خلال نصف دقيقة.»;
- the two actions that are not the current state, as buttons: «افتح الموقع», «اعرض صفحة قريباً», «ضع الموقع في الصيانة»;
- after a change: «تم. الموقع الآن: صيانة.» (the state read back, not the one sent).

### Exact paths

Product (inside the lock; add them to its allowlist before writing):
- `supabase/migrations/<timestamp>_site_state.sql`: table `public.site_state`, one row (`id boolean primary key default true check (id)`, `mode text not null check (mode in ('open','soon','maintenance'))`, `version integer not null default 0`, `updated_at timestamptz not null default now()`, `updated_by uuid references auth.users (id) on delete set null`), seeded `soon`: the migration must not change what the live domain shows, and the launch is the owner pressing «افتح الموقع». RLS on, with a select policy and column grants, so the public reads one word and nothing else: `grant select (mode) on public.site_state to anon; grant select (mode, version) on public.site_state to authenticated;`. No insert, update or delete policy or grant. `site_state_set(p_actor uuid, p_expected_version integer, p_mode text)`: security definer, following `commerce_checkout_set` in full: the owner recheck, the row locked with `for update` before the version is compared with `is distinct from`, a stale version refused with 23505, the row written, an audit row (`'site.state'`, `'site_state'`, with `{from, to, version}`), the new version returned. Execute revoked from `public`, `anon` and `authenticated`; granted to `service_role`.
- `supabase/functions/_shared/site-state.ts`: the Zod schema of the action body (`{ action: 'site-state-set', mode, expectedVersion }`, strict), shared with the browser form the way `commerce-settings.ts` is.
- `supabase/functions/_shared/admin.ts`: the case `site-state-set`: owner only, `STEP_UP_REQUIRED` without a fresh TOTP, then the RPC; 409 on a version conflict.
- `src/components/admin/SiteStateForm.tsx` and its mount in `src/components/admin/SettingsView.tsx`. The form reads `mode, version` from the table itself; there is no new read RPC.
- `src/components/admin/StepUp.tsx`: its input id comes from `useId()`. The settings page will hold two `StepUp` dialogs (the store's and this one), and today's fixed `id="step-up-code"` would be duplicated.
- `PLANS/DATA-AND-SECURITY.md`: the table's row.
- Tests: `tests/unit/admin-site-state.test.ts` (the action: editor refused, no TOTP refused, bad mode refused, conflict, success). `tests/integration/site-state.test.ts`: anon reads `mode` and is refused `version`, `updated_by` and `*`; an authenticated owner's PATCH, POST and DELETE on the table are refused; `site_state_set` cannot be executed by `anon` or `authenticated`; it refuses a non-owner actor; of two calls with the same expected version exactly one succeeds; the audit row. One case in `tests/e2e/owner-operations.spec.ts` (the owner sees the section first, switches with the code, the sentence changes; an editor does not see it), restoring the row in `afterAll`.

Outside the product (no lock needed):
- `artifacts/soon/worker.js`: read the state from `GET <SUPABASE_URL>/rest/v1/site_state?select=mode` with the publishable key (two Worker variables, both public values), remembered for 30 seconds per isolate, with a 1.5 second timeout. Anything other than a 200 with exactly one row holding one of the three words is a failed read, and a failed read is remembered for the 30 seconds like a good one. A failed read keeps the last answer; with no answer yet it uses `MODE`, which is `soon` before the launch and `open` from the launch (`worker.js` and `deploy.cjs` accept `open`; P11 sets it), so a database that cannot answer never puts «قريباً» over the launched site. `MODE = "maintenance"` set by a deploy wins over the stored state: that is the switch for a restore or any work that takes the database itself down. `open` passes the request through to the site only when the gate runs on a route in front of the Pages project (a variable P11 sets, for example `GATE_ORIGIN=pages`); anywhere else `open` is treated as `soon` (SOON-03). Until P11 moves the domain, the Worker is itself the domain's origin, and `open` would make it fetch its own hostname: Cloudflare re-enters the same Worker up to 16 times and ends in error 1019 (the audit read Cloudflare's Custom Domains and Workers errors pages on 2026-10-07). So the hosted acceptance runs the three states against a separate test hostname with its own row, or treats the `open` switch as the launch itself. In `soon` and `maintenance` these addresses still pass through, so the owner can always switch back and no buyer or subscriber is stranded: `/admin`, `/admin.txt`, `/admin/*`; P08's pages that a mail or the payment page sends a person to: `/checkout/return` (Moyasar's `success_url` and `back_url`), `/orders` (the link in every order mail), `/notify/confirm` (the confirmation mail, whose link lives 7 days) and `/notify/unsubscribe` (in every availability mail); `/book/*` (the admin's preview reads it); `/policies/*` (the order page links the policy a buyer agreed to for a return, and the policy pages carry no shop controls; PLAN-GAPS-14); `/robots.txt` and `/sitemap.xml` (SOON-05: Google asks that robots.txt is never answered with a 503, and for a server error it stops crawling the site for the first 12 hours while it keeps trying to fetch robots.txt; Google's pause guidance and robots.txt pages, read by the audit on 2026-10-07; the soon site also needs a static `robots.txt`, so crawlers spend no script run); and the site's static files (`/_next/*`, `/fonts/*`, `/images/*`, `/brand/*`, `/media/*`, the icons). `/store/*`, `/cart` and `/checkout` stay behind the gate: they are the shop itself, which `soon` hides and `maintenance` takes down; the store's own pause is the «الشراء» switch, and a hold on `/checkout` only expires (the payment page returns to `/checkout/return`).
- The gate's decision is one pure function (the state, the path, the last answer and `GATE_ORIGIN`) with one `node --test` file beside it in `artifacts/soon/`: the exempt paths (`/notify/confirm`, `/policies/*`, `/robots.txt` and `/sitemap.xml` included) and their near misses, the failed-read fallback, and `open`: passed through behind a route to the Pages project (`GATE_ORIGIN=pages`), treated as `soon` anywhere else.
- `artifacts/soon/deploy.cjs`, `wrangler.toml`, `README.md`.

### What P11 decides

The launch sequence (also in `PLANS/WORK-PACKAGES.md`, P11): At launch: put the gate P11 chose (a Worker route or a Pages Function, from the Cloudflare docs) in front of the Pages project, reading the stored state, which is still `soon`; take anas.studio and www off the Worker `anas-studio-soon`, attach anas.studio to the Pages project, so the domain keeps showing «قريباً», and give www a proxied placeholder record answered only by a zone redirect rule to the apex (301, path and query kept), never a second host on the project, since the functions accept one origin (EF-ACCESS-03, ISSUES I32 (11)); then the owner opens the site with «افتح الموقع»; then `MODE = "open"` (below). The Worker `anas-studio-soon` is deleted once nothing routes to it (D46). The order is the point: the real site is never on the domain without the gate in front of it.

Where the gate stands in front of the real site, chosen from the Cloudflare docs and recorded with their address, not recalled: a Worker route in front of the Pages domain, or a Pages Function (`_middleware`) with `_routes.json` so that only pages, not files, call it. Either way the free plan's daily request allowance is checked against measured traffic first. Until the hosted Supabase project has this migration, the domain keeps following `MODE`.

Also decided there, from the docs:

Whether a launch period on Workers Paid is worth it is the owner's decision with E07 (`docs/costs.md`); the ceiling belongs in `artifacts/soon/README.md` and in P11's traffic check.

## Rules

- Truthful states: the form shows the state it read back; a failed read says «تعذّر قراءة حالة الموقع», never a guess. No return time is promised anywhere; `Retry-After` is for crawlers.
- Security: owner only, fresh TOTP, the SQL rechecks the owner, every change is audited, and the public can read one word and nothing else. An editor cannot take the site down. The gate never serves a design on `/admin`.
- The store's own pause stays the «الشراء» switch (P08). This switch does not touch orders, holds or payments; the Edge Functions keep answering in every state. The gate hides pages only: the payment callback and webhook are Edge Functions and `/checkout/return` is exempt, so a buyer whose checkout tab was open before the switch can still pay. Hence, before a restore or a migration (SOON-04): close «الشراء» on the project being replaced, wait until no hold or unpaid invoice is open (a hold lasts 20 minutes and `checkout-expire` ends it), then switch to «صيانة», and reopen «الشراء» only after the restored project is verified (`docs/operations.md`, "A real restore into a new hosted project", step 1). One exception: while the state is not `open`, P08's availability sweep does nothing, as it does while checkout is off, because its mail links to `/store/<slug>`, which the gate hides, and each subscriber is told only once per revision. The SITE-STATE-1 migration replaces `finance.availability_sweep()` with one more condition, `(select mode from public.site_state) = 'open'`, beside `checkout_enabled`, and changes nothing else; `tests/integration/site-state.test.ts` proves that a restock in `maintenance` with checkout on queues no availability mail and that the first sweep after `open` queues it once.
- **Open decision for the owner (SOON-01): what «قريباً» answers after the first opening.** The soon answer is 200 with `X-Robots-Tag: noindex` on every gated address (`artifacts/soon/site/_headers`, which this package does not change). Google's guidance for pausing a site says "Don't block the website by returning 403, 404, 410 HTTP status codes, or with a noindex robots meta tag or x-robots-tag HTTP header. This will remove the website's URLs from Google Search." (read by the audit on 2026-10-07). So once the site is launched and indexed, one press of «اعرض صفحة قريباً» can drop the gated pages from Google until they are recrawled after the site opens again, and the approved admin sentence does not say so. D47 defines the three states; the contract keeps them and does not choose. The owner chooses, and either way the admin's sentence says it: (a) record that the site has been opened (a `launched_at` set by the first `open`, or a gate variable P11 sets) and answer «قريباً» from then on like maintenance, 503 with `Retry-After` and no noindex; or (b) hide «اعرض صفحة قريباً» after the launch.
- **What visitors see is not always the stored word** (SOON-06, SOON-07). A `MODE = "maintenance"` set by a deploy wins over the stored state, and `MODE` answers when reads fail, while the form shows the stored word and the availability sweep follows it too. «صيانة» also does not hold through a database outage: an isolate that starts after the reads began failing (a new data centre, an evicted isolate: Cloudflare says isolates are not long-lived, read 2026-10-07) has no last answer and falls back to `MODE`, which is `open` after the launch, so only a deploy of `MODE = "maintenance"` holds then, and the admin's «صيانة» line should say a database outage needs the deploy switch. Proposed, not decided: a second level before `MODE` (each good read also `caches.default.put` a small response holding the word with a long max-age, and a failed read with no in-memory answer reads it back from the data centre's cache), and a header such as `X-Site-State: maintenance; source=deploy|stored|fallback` that the form reads with a same-origin HEAD of `/` to show a line when it differs from the stored word. Until then, during maintenance done by a deploy also set «صيانة» in the admin, so the sweep waits, and end the work by redeploying the normal `MODE`.
- Not in this package: a schedule, a message the owner edits (the pages' words are files; changing them is a deploy), choosing which designs rotate, a state per page.
