# Data and security contract: Supabase content plus private transactions

One Supabase PostgreSQL database. Content, staff and media tables live in `public`, exposed to the Data API with RLS enabled on every table. Transactional data lives in `finance`, which is not exposed. UUID IDs, UTC timestamps, one migration history in `supabase/migrations/`; all money is integer SAR halalas.

SITE-STATE-1 adds `site_state.mode`. A column added to any of these tables without a column-list grant would be readable with the publishable key. Scheduled content enters `published_documents` only when `publish_due()` publishes it; archiving removes it. A scheduled document that fails to publish drops its schedule and is audited as `content.publish_due_failed`; the others still publish. A save, publish or schedule based on an older version than the latest conflicts (409, raised as `unique_violation`, 23505: the commerce settings save and the policy approval use the same code, never 40001). A post whose slug another live post uses cannot be scheduled or published. A post with `visible = false` stays out of public lists and pages.

## Authorization and DB proof

Two kinds of database identity. **People** use the Data API as `authenticated` (staff JWT) or `anon` (public), and RLS decides per person through the `staff` helper. **Services** are the Edge Functions, which call named SQL functions through the Data API as `service_role` (D32; its key exists only inside Supabase), plus the migration identity: the Supabase CLI applies migrations as `postgres` from local or CI only. Server-only functions are granted to `service_role` and revoked from `anon` and `authenticated`. The server-only functions are `security definer`, owned by the migration role `postgres`, with `search_path = ''` and fully qualified SQL; no separate owner role exists (D32). `anon` and `authenticated` have no grants on `finance`, which is not exposed in the Data API. Revoke PUBLIC function execution and public schema creation.

Editor manages public content and media; operations sees orders, email problems and bookings and changes fulfillment; owner configures catalog, prices, coupons, shipping, team and policies and issues refunds. Owner statistics and boards are owner-only. Privileged functions recheck the caller's active role from `auth.uid()`, or, for Edge Function calls made on behalf of staff, from the user id of the JWT the function verified; never from a request's actor_id. Refunds, role changes and invites require `aal2` with a TOTP entry in `amr` newer than 5 minutes. No per-request SET ROLE or session identity left on pooled connections.

Test the Data API with real JWTs for anon, editor, operations, owner and a revoked owner, and test the server-only functions as `service_role` and their refusal for `anon` and `authenticated`. Generic table writes cannot change stock holds or order totals, or issue refunds. No secret/service-role key or migration credential in the static site or browser. `pnpm check:export` fails on exactly these shapes in `out/`: a Supabase secret key (`sb_secret_`), a Svix webhook secret (`whsec_`), a Resend API key, a PEM private key, a Moyasar secret key (`sk_test_` or `sk_live_`, which also catches the local emulator's key), the three local development secrets (jobs, token pepper and the local Moyasar webhook secret) and a service_role JWT. It does not recognise a Postgres connection string (`DATABASE_URL`), a Supabase access token (`sbp_`), the database password, a Cloudflare token or the Turnstile secret: those stay out of the build only by never being a `NEXT_PUBLIC_` variable or part of the Pages build environment (`.env.example`); nothing detects them. Functions use fixed `search_path=''`, fully qualified SQL and no caller-selected SQL or table names. All transaction invariants are enforced in the database.

## Checkout transaction

1. Browser stores only variant IDs, quantities and cart schema version in localStorage. Never trust its totals; discard malformed/unknown variants. A cart can survive reload, but quote/prices are fetched again. Storage denial still permits session cart. No customer/address data in localStorage; the dedication and the create idempotency key with a digest of the request stay in sessionStorage and go with the tab.
2. Quote resolves enabled product/variant and owner-set prices, policy setup, city shipping and coupon eligibility. Empty cart, mixed booking plus physical items, unknown/disabled variant, too many lines (>50), quantity outside 1–20 or invalid dedication fails. One booking per order; ordinary physical/digital mixed cart is supported. Sum and discount in integers; no float rounding. Proportionally allocate discount to lines with deterministic remainder so refunds reconcile exactly.
3. Final POST uses an idempotency key; same key+same payload returns same order, same key+different payload returns 409. Lock variant rows in sorted ID order, coupon row and booking reservation. Recheck versions and availability. Reserve all resources and write order/items/policy snapshots/outbox in one transaction or none. Hold default 20 minutes, invoice expiry no later than hold expiry. A paid booking has the same expiry rule.
4. Create the invoice outside the DB transaction with a durable attempt in `creating`. Store its ID and URL, then return it. Never hold SQL locks across network calls. On timeout mark `uncertain`; reconcile using the stored provider reference/idempotency contract, never blindly issue duplicate invoices. If provider creation has no documented idempotency support, do not invent a header: reconcile first or cancel/review the uncertain attempt. A second concurrent request cannot create a second active payable attempt for the order.
5. Redirect/success query parameters are display hints only. Until authoritative verification finishes, show «جارٍ التحقق من الدفع» with a safe refresh. Do not clear the cart or issue downloads on a callback status string.
6. Webhook: verify documented `secret_token` with constant-time comparison and validate `live` matches expected mode. Persist an event ID durably before ACK, then fetch gateway payment and invoice with secret credentials. Check exact invoice/attempt mapping, account/environment, payment status, expected full amount, currency and refund fields. The unique invoice mapping is the order binding; metadata alone is insufficient. Do not assume every webhook has the same payload shape. Invoices' callback endpoint is only a prompt to reconcile; use the same fetch checks, not an invented HMAC scheme.
7. `apply_verified_payment` locks order, attempt and reservations. The first fully verified paid result commits stock/coupon/booking, grants digital entitlement if asset ready, and queues one receipt; duplicate/reordered events do not repeat any of these. `authorized`, `verified` or merely `initiated` is not paid. Record partial/over/under currency or amount mismatch for review; never fulfill it. A payment the provider already shows refunded in full when it is first verified is a review payment too (`REFUNDED_BEFORE_SETTLE`) and is never fulfilled; one refunded in part is committed and that refund is recorded with it.
8. If payment arrives after a reservation expired, reacquire stock/slot transactionally. If unavailable, set `paid_needs_resolution`, do not oversell or promise the appointment, and notify owner for refund/rebooking. The money remains recognized; it is never relabelled failed because fulfillment failed. The owner's resolution (`order_resolve`) is refused while a refund of the order is in flight (`REFUND_IN_FLIGHT`), when the money has gone back at the provider (`PAYMENT_REVERSED`: voided, or the refunded total has reached what was captured) and when a line is not available (`STOCK_UNAVAILABLE`). Free an expired held slot before a new reservation; exclusion constraint prevents two active overlaps.
9. Reconcile pending/uncertain attempts every minute in bounded batches, backing off after repeated provider errors; keep manual retry on owner order view. Durable events/outbox survive function restarts. Webhook retries are finite, so webhook-only completion is not adequate. Work of the other payment mode cannot be checked with the configured key: the job parks it (`MODE_CHANGED`), alerts the owners, lists it on the reconciliation screen and keeps its order from erasure, and `PAYMENTS_MODE` changes only with nothing in flight (docs/payments-runbook.md, "Changing the payment mode"). After payment a paid attempt is read again only by the webhook or the owner's recheck; a webhook outage is an operations procedure (docs/operations.md).

## Unpaid reservation abuse

Unpaid-hold protection applies before both stock and booking reservation. Use server-validated Turnstile, bounded attempts and transactionally enforced active-hold limits by guest checkout session (one unexpired pending order per session, under its advisory lock), 10 creates an hour per salted IP hash and 500 orders a day; there is no per-recipient limit (P08-CONTRACT 13.1) and no per-resource limit, so one address can hold 200 units of a variant per 20-minute window, a business choice that is still the owner's to make (docs/operations.md, "Checkout holds and limits"). Rotating idempotency keys cannot reset the existing hold's expiry or bypass those limits. Keep IP throttling secondary so shared networks remain usable; record concrete thresholds and residual distributed-abuse limits. Expired holds are reclaimed and same-request retries reuse the original order. No buyer account or paid fraud service is required.

## Refund, return and delivery

Owner MFA confirms amount/reason on the order. Create a refund intent under lock; reserve refundable balance including pending/uncertain intents so simultaneous refunds cannot exceed payment. Call gateway outside transaction. On response timeout remain uncertain and fetch authoritative payment/refund state before retry. Only confirmed gateway state marks financial refund succeeded. Refund replays dedupe on the idempotency key and request hash, with one refund in flight per payment; webhook events dedupe on the event id. A request carries the confirmed refunded total it was built from, and another total is refused `STALE`; a payment whose latest chargeback row is against the seller is refused `CHARGEBACK_RECORDED`; an external refund can still be recorded. Partial refunds allocate to order items; revoke only affected digital entitlement/booking, preserve unaffected items. Full refund revokes all entitlements. Do not automatically restock shipped/returned goods before owner marks them received and sellable.

Digital receipt links lead to scoped tokens, never the raw Storage key. Order-access links expire after 7 days and may be reissued after a generic email recovery request; the shipped and refunded mails renew them, and the owner can rotate one and re-send it, to the same or a corrected address (`order_link_reissue`, the old link stops opening at once); a download token expires after 15 minutes, at most 3 issuances, with a 60-second signed Storage URL (the `download` function, D32). Token hashes use one server pepper (`TOKEN_HASH_PEPPER`), unversioned: it cannot be rotated without re-issuing every link, so a leak is an owner decision, not a procedure (docs/operations.md, "Rotating a secret"). A leaked already-issued signed object URL remains usable until its short expiry; do not promise instantaneous DRM. Use `Referrer-Policy: no-referrer`, attachment disposition with a safe UTF-8 filename and `X-Content-Type-Options: nosniff`. Refund/revocation prevents new links.

Physical orders require supported shipping address and phone; digital-only orders do not request address. Operations marks preparing, shipped and delivered, never for an item a dispute stopped (`FULFILLMENT_STOPPED`) or one a refund in flight allocates (`REFUND_IN_FLIGHT`); the carrier and tracking of a shipped item are corrected on purpose, not by a second shipment; tracking and customer emails use dedupe keys. Signed edition supports dedication text and a fulfillment checklist. Returns start as customer requests and have a staff trail. Record all financial and stock changes in audit, not only the last status.

## Disputes and payout reconciliation

Disputes and payout discrepancies are separate from refund success. An owner verifies provider evidence and records an immutable, redacted audit entry with payment/payout reference, amount, reason, date and resolution. Changing fulfillment or entitlement requires an explicit recorded decision (`fulfillment_stopped` stops the shipping of the named items while it is the reference's latest row; `entitlement_kept` grants again what an earlier `entitlement_revoked` row of the reference revoked); never overwrite the original payment or manufacture a refund to represent a chargeback. The existing gross-minus-confirmed-refunds metric must disclose that it excludes gateway fees, chargebacks and payout timing; it is not bank-settled cash. Manual reconciliation reports those differences separately and avoids counting one adjustment twice.

## Privacy requests and restore obligations

Keep a minimal deletion ledger outside the database being restored, within the approved protected backup arrangement. It records identifiers and actions (erasures and staff revocations), not erased content, so restoring an older backup cannot also roll back the evidence needed to reapply later deletions. A restore replays the erasures that need no secret (contacts, buyers) at once, before any Vault value, function secret or deployed function exists, so nothing can have sent the mail an erasure removed; it replays the staff revokes and erasures in SQL at the same step, because Auth and its users come back with the database and a restored member is active again (the revoke sets `active = false`, which RLS and every staff function check, so it comes first; the erase function refuses an active member) (docs/operations.md, "A real restore into a new hosted project", step 5). The ledger holds a buyer's address in plain text and is in no backup, so it needs a protected second copy of its own (docs/privacy-data-map.md).

Privacy requests require verified identity and an auditable access/export/correction/deletion procedure across customers, orders, contacts (including the owner's mailbox copy, D31), subscriptions and logs. Export only that person's data, excluding staff notes and private boards. Preserve legally required accounting records and document the reason and approved retention. Record deletions so a backup restore reapplies them before reopening service; no schedule for retained backup copies exists: D35 sets none and nothing prunes a backup file, so erased data lives on in every file made before the erasure, and a retention for the files is E08's decision with the owner (docs/privacy-data-map.md). Test with synthetic records and document exceptions rather than promising immediate erasure from every backup.

## Email delivery and retries

All email senders consult suppression before dispatch, except that staff mail (a contact notice or an owner alert) is never held back by the list (round M1b). Verified hard-bounce/complaint events suppress further sends (a Transient or Undetermined bounce only records the event); other failures follow documented provider semantics and bounded backoff. Store retry limits, next retry and exhausted state; surface recovery in existing admin operations. A manual replay preserves business dedupe, rechecks unsubscribe/suppression and uses the documented provider idempotency lifetime. An ambiguous send outside that lifetime needs reconciliation before retry. Three tiers by priority share the day's `DAILY_QUOTA`: priority 0 (receipts, shipping, refund and file-ready notices, owner alerts) goes up to `DAILY_QUOTA - 5`, because the last five sends of the day are kept for sign-in codes (Supabase Auth's SMTP on the same account, not the outbox, so not counted); priority 1 (contact notices and order-link recoveries, at most 20 links a day) stops at `DAILY_QUOTA - RESERVE`; priority 2 (confirmations, at most 30 a day, and availability notices) stops at `DAILY_QUOTA - RESERVE - LOW_RESERVE`. A refusal of the account itself (401 or 403: a revoked key, an unverified domain) is a `PROVIDER_CONFIG` retry that uses no attempt, waits 15 minutes and stops the run. A person can close an uncertain or exhausted mail as handled (`outbox_close`). A provider quota 429 (daily or monthly) is a QUOTA retry that uses no attempt and waits for the next 00:00 UTC. A run that claims nothing while mail is due is recorded `partial` with the reason `QUOTA_HELD`, and the owner home says mail is held. The contact form's daily cap (40, `contact_submit`) is sized so one day's notices for up to two notified recipients fit under `DAILY_QUOTA - RESERVE`. Never claim unlimited exactly-once delivery.

## Media and session boundaries

The admin media library stores objects in Supabase Storage (D32): originals and the quarantine in the private `media-private` bucket, checked WebP derivatives in the public `media-public` bucket, whose bucket rules accept `image/webp` only and which only the service role writes. The upload flow generates bounded WebP derivatives in the browser at 360/720/1200/1800px without upscaling, cropping with browser controls. No sharp import or Cloudflare Images dependency. A server-owned ticket and key (5-minute expiry), magic-byte/MIME/dimension/size checks and authenticated ownership gate promotion out of private quarantine. Permit JPEG/PNG/WebP/AVIF originals <=15MiB/40MP and PDF <=100MiB; reject user SVG, HTML and archives. Header validation is not full image decoding or a guarantee of metadata sterilization. Serve accepted public images from an isolated origin (the Supabase Storage host, never the site's); the original stays private. Whether that origin sends nosniff is a hosted check (I32). Regeneration and crop happen in the authenticated browser; a failed or unsupported encode leaves an actionable error, never a raw fallback publication. Rights and alt are required; references block destructive removal.

PDFs remain private; pdfjs-dist 6.3.289 pinned (it has no eval path: isEvalSupported was removed upstream), local version-matched worker, enableXfa:false, no PDF JS/actions/attachment auto-open (`docs/book-preview.md`). Approved excerpt is separate bytes, not client-hidden full manuscript. Manifest hash/range/rights required.

Supabase Auth sessions, passwordless sign-in (an 8-digit email code asked for behind Turnstile, or Google), sign-up disabled, and the Supabase Auth rate limits. Re-read the active role on every query. Owner step-up is Supabase TOTP at aal2; the MFA verify limit is fixed at 15 per minute per IP. Passwordless is enforced by a Custom Access Token hook (`public.deny_password_tokens`, 403 to a password grant), the only control: `secure_password_change = true` only asks a session older than 24 hours to reauthenticate before it sets a password (VENDOR-PLAT-03, ISSUES I55 (4)); the hosted project enables both (I28). Removing a staff member sets active=false, bans the Auth account and deletes the member's Auth sessions and refresh tokens (`staff_sessions_end`, which `staff-admin` calls after the ban; rounds M1b and F1). An access token already issued lives until it expires (`jwt_expiry`), and every staff function and RLS recheck the active row meanwhile. Saves carry the row version; a conflict keeps unsaved content, and restore appends a new version. No second editor state store.

CSP consistent with Next and the Supabase origin, local PDF.js workers, restrictive admin frame-ancestors, same-origin mutations, no unsafe eval, nosniff and private no-store. Today `public/_headers` sends `object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'` on `/*`; the full CSP is P10's (`public/_headers`, or a build step writing `out/_headers`, with a check in VERIFICATION.md and `tests/e2e/security.spec.ts`): `style-src 'self' 'unsafe-inline'`, `script-src 'self' 'unsafe-inline' https://challenges.cloudflare.com` without `unsafe-eval`, `frame-src https://challenges.cloudflare.com` (Turnstile's iframe; Cloudflare's Turnstile CSP page, read by the audit on 2026-10-07), `img-src 'self' data: blob:` plus the Supabase project origin (every library image is served from its Storage host, and `media-src` for the films' host if I33 moves them), `font-src 'self'`, `worker-src 'self'`, `connect-src 'self'` and the Supabase Data API and `/functions/v1` origins, the Cloudflare Web Analytics hosts only if the beacon is enabled, and a check against the hosted preview. Safe Lexical renderer allows known nodes/marks/HTTPS links/media IDs only, no arbitrary HTML/embeds. Bidi isolation, escaped email/calendar fields, request IDs, no secrets/payment/card/PII logging. Sentry beforeSend scrubs tokens, bodies, email and addresses; no replay. Backups encrypted and restored to disposable environment first. Automatic destructive purge never removes unapproved accounting records.
