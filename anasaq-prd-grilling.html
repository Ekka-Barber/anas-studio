ROUND 1 — FATAL: The tech stack contradicts itself 5 questions
Q1Cloudflare Pages + Next.js App Router + Server Components — which is it? UPDATED Jul 2026
The PRD says Cloudflare Pages (Section 2) AND Server Components async function Page() (Section 6). The original grilling claimed these conflict. That is now partly out of date.
  • The old @cloudflare/next-on-pages (Edge-only) is being superseded by the OpenNext Cloudflare adapter for Workers (1.0-beta+), which supports Next.js 14/15 App Router, Server Components, Server Actions, ISR, and dynamic routes on Cloudflare Workers.
  • "Static export" (Section 2's escape hatch) still disables Server Components — that part of the original claim remains true.
So which is it: (a) OpenNext on Workers (new — keeps most of what the PRD wants), (b) static export + client-only, or (c) deploy to Vercel and drop the $0 rule? Path (a) is now viable and was not when this sheet was first written.
Update (Jul 2026): The original "where to check" pointed at next-on-pages. The new source of truth is the OpenNext Cloudflare adapter. It still has edge cases (see the 2026 community reports of Kinde/next-intl pain), but Server Components are no longer automatically dead on Cloudflare.
Plain English What the fight is about: Next.js (the framework) can render pages on the server as they're requested — but Cloudflare's cheap/free hosting historically only allowed a stripped-down "static" version. The PRD asked for both, which used to be impossible. What changed: A new bridge tool ("OpenNext") now lets full Next.js run on Cloudflare's free Workers. So the conflict is mostly gone — but it's still beta, and you should pick the path explicitly so the developer isn't guessing. The real decision now: are you OK using a beta-age tool to keep $0/month, or would you rather pay Vercel ~$0–20/mo for the officially-supported path?
Where to check: Read the OpenNext Cloudflare page + the Cloudflare blog "Deploy Next.js Apps to Cloudflare Workers with the OpenNext Adapter." Try a hello-world App Router deploy before committing the whole site.
Q2"$0/month" vs Supabase free-tier auto-pause UPDATED Jul 2026 — worse than first stated
Supabase free tier pauses the DB after 7 days of inactivity. The original sheet said this causes a "5–20s cold start." That's optimistic. Per multiple 2026 reports (and Supabase's own docs), a paused project does NOT auto-wake on a visit — it must be manually restored from the dashboard. So the waitlist form doesn't just feel slow, it throws errors until someone logs into Supabase and clicks "restore." For a low-traffic personal site, this is the textbook failure case.
Update (Jul 2026): Verified against Supabase's pricing page ("Free projects are paused after 1 week of inactivity") and 2026 community reports confirming no auto-wake. The fix is a scheduled "heartbeat" (a free GitHub Actions cron that pings the DB every 1–2 days) — or upgrade to Supabase Pro (~$25/mo in 2026, up from $9).
Plain English The free database falls asleep if nobody uses it for a week, and it does NOT wake itself up when a visitor arrives. Someone has to go into the database's control panel and press a button to restart it. Until that happens, your "join the waitlist" form will simply fail. What to do: Either (1) set up an automated daily "poke" that keeps the database awake (cheap, free, your developer can do this in ~15 min), (2) pay Supabase ~$25/month so it never sleeps, or (3) accept that the form will sometimes be dead for hours until you notice and fix it. Recommend (1).
Where to check: Supabase docs → "Project Pausing." Search GitHub for supabase-pause-prevention (a ready-made GitHub Actions workflow).

Q4Have you verified RTL behavior of Aceternity / Magic UI / Shadcn? VERIFIED Jul 2026
All three are LTR-first, none ship RTL. The hero's TextGenerateEffect animates character-by-character — Arabic letters join and reshape, so mid-animation the word renders as disconnected, broken Arabic. Hardcoded translateX / left / right everywhere. (Confirmed: this is a well-documented class of bug for cursive scripts — same issue hits Hebrew and Persian.)
Plain English The fancy "text fades in letter-by-letter" animations are designed for English and break Arabic. Here's why: in English, splitting "HELLO" into H-E-L-L-O and revealing each letter looks fine. But Arabic letters connect to each other like cursive handwriting — the shape of each letter depends on its neighbors. If you split "مرحبا" into individual letters and reveal them one at a time, each letter shows in its disconnected form, so mid-animation the word looks like gibberish. What to do: Before building anything, ask the developer to make a 5-minute test: take one animation, put an Arabic sentence in it, record a phone video. If it looks broken (it will), either (a) have the developer build a custom Arabic-friendly version, or (b) pick a different animation style that reveals whole words at once instead of letters. Test this now — it's cheap to test and fatal to discover late.
Where to check: Copy TextGenerateEffect from aceternity.com into an dir="rtl" CodeSandbox with an Arabic string. Screenshot it. A 5-minute task that decides the whole hero section.
Q5Which Tailwind version? RTL support differs massively VERIFIED Jul 2026
Tailwind v3 logical properties (ps- pe- ms- me- start- end-) are partial. Tailwind v4 has native logical properties out of the box — and v4.2 (2025) is described as the "most impactful" update for bidirectional layout, completing coverage for spacing and borders. PRD never pins a version.
Plain English "Tailwind" is the styling tool the developer uses to position things left/right. Older versions were built for English (left-to-right) websites, so "padding-left" was baked in everywhere. For an Arabic (right-to-left) site, that's a constant headache — every "left" has to be manually swapped to "right." The newer version (v4) understands direction automatically — you say "padding on the start side" and it figures out whether that's left or right based on the language. This saves dozens of bugs. Decision: use Tailwind v4. It's the single biggest RTL win for the least effort.
Where to check: Decide now (recommend v4). Audit every utility: ml-4, left-0, right-2, -translate-x-1/2 = flag for logical-property conversion. Third-party plugin tailwindcss-logical now recommends migrating to v4.

Q13100vh on mobile is broken — use 100dvh UPDATED Jul 2026 — new iOS 26 wrinkle
Mobile Safari's 100vh includes the address bar. Hero is 10–15% too tall; scroll indicator hides behind URL bar. 100dvh is broadly supported (Safari 15.4+, Chrome 108+, Firefox). New wrinkle (2025/2026): reports of a Safari iOS 26 regression where 100dvh no longer fills the viewport correctly in some cases. Not fatal, but means iOS 26 needs hands-on testing.

Plain English "Make this section full screen height" sounds simple but is famously broken on iPhones. The iPhone's Safari browser has a address bar that shrinks/grows as you scroll, so "full height" keeps changing — the result is the bottom of your hero section (e.g., a "scroll down" arrow) gets hidden behind the address bar. There's a newer measurement unit (dvh = "dynamic viewport height") that adjusts itself — it mostly fixes the problem. What to do: tell the developer "use 100dvh everywhere, not 100vh, and test on a real iPhone before we ship." This is a known, solvable issue — just needs to be on the checklist.

Q14Zero spam protection on public-insert forms — fails in ~48h
RLS "public insert" = anyone with the anon key (public in your JS bundle) can INSERT. Bots fill tables with garbage fast. No rate limit, no captcha, no honeypot, no email verification.
Where to check: Add (≥1): Cloudflare Turnstile (free, fits stack), honeypot field, server-side rate limit (you may not have a server — Q1), email verification before counting a waitlist row.
Plain English Any form on a public website gets flooded with garbage within about 48 hours. Bots scan the internet for unprotected forms and fill them with spam — thousands of fake emails, scam links, etc. The "waitlist" and "contact" forms in the PRD have zero protection. Within days, Anas's database will be full of junk and the real signups will be buried. The fix is a "captcha" — but the modern kind is invisible. Cloudflare Turnstile is free, made by the same company as the hosting, and usually doesn't even show a puzzle to the user — it quietly verifies they're human in the background. Recommendation: add Turnstile to both forms. It's a 30-minute task for the developer and saves a permanent headache. Bonus: add an extra hidden "honeypot" field that real users never see but bots fill in — if it's filled, reject the submission.
Q15No email validation, no duplicate UX
book_waitlist.email is unique (good), but what does a returning user see on re-submit? A 409? A friendly message? Undefined. No regex/format validation.
Where to check: Define the 4 form states: empty/invalid → success → already-exists → network/server error. Each needs copy + a toast variant.
Plain English When someone submits the waitlist form, several different things can happen, and the website currently has no plan for most of them. A "toast" is that little temporary popup in the corner (like "Saved! ✓"). The 4 scenarios that need a message:
  1. Email is missing or fake-looking → "Please enter a valid email."
  2. Success → "You're on the list! We'll be in touch."
  3. They already signed up before → "Looks like you're already on the list 🙂" (NOT a scary red error).
  4. The site is broken / no internet → "Something went wrong. Please try again in a moment."
Each message should be written in Arabic and shown in a small popup. Without these, users see either nothing or a confusing error code. Write all 4 messages now — it's a content task, not a tech task.

Q17Schema inconsistencies
gallery_scenes.category enum (Section 4) = أماكن, مشاريع, منتجات, رحلات, كواليس. Section 7 UI filter = خلف الكواليس (different label). Pick one canonical set. No created_at DEFAULT NOW(), no sort order, no is_published flag. Arabic enum strings in Postgres are fragile — consider category_key (e.g., places) with Arabic labels in UI.
Where to check: Re-author schema with defaults, indexes, canonical category list. One source of truth.
Plain English Three small but real problems in how the photo database is described:
  1. Two different lists of categories. The database section calls one category "أماكن" (Places) but the website filter calls it "خلف الكواليس" (Behind the scenes). These must match, or the filter button won't find the photos.
  2. Arabic words used as database codes. Databases work best with short English codes (like places) and show the Arabic word only to humans. Storing Arabic directly as the code is fragile — typos, encoding glitches, and the whole system breaks.
  3. Missing basics. No "date added" (so you can't sort newest-first), no "published/draft" toggle (so Anas can't prepare a photo without it going live).
Fix: Use English keys internally (places, projects, products, trips, behind_the_scenes), show Arabic labels on the website, and add date + published flag to every photo row.
Q18RLS read policy for the gallery is unspecified
"Public inserts for forms, only authenticated reads" — but the gallery must be public-read for the site to work.
Where to check: State the three policies explicitly: book_waitlist (anon insert, no read), contact_messages (anon insert, owner read), gallery_scenes (anon read, owner write).
Plain English "RLS" (Row-Level Security) = the database's bouncer. It decides who's allowed to do what. For each of the three tables, you need to set the rule. Think of it like a building with three doors:
  • Waitlist (book_waitlist): Any visitor can drop a name in the box (insert), but nobody can read the list except Anas. (Otherwise anyone could scrape all the emails.)
  • Contact messages: Same — anyone can send a message, only Anas can read them.
  • Gallery photos: Opposite — everyone can see the photos (otherwise the site is blank), but only Anas can add/change them.
The PRD's wording is fuzzy and could leave the photos unreadable OR leave everyone's emails exposed. The three rules above are the correct version. Confirm them in writing.
