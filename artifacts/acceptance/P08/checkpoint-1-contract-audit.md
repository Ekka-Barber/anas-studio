# Checkpoint 1: the contract audit (workflow wf_f7b37a3f-3c7, five Opus auditors, 2026-10-02)

## Lens A: Provider boundary and the emulator (P08 checkpoint 1). Provider facts taken only from artifacts/acceptance/P08/moyasar-docs-2026-10-02.md and contract section 2; WebFetch could not be loaded in this a
Verdict: audit_failed

### A-PB-01 [critical] 6 refund_settle / payment_reconcile_claim; 7 refund-create, refund-recheck; 1 paymentsConfig
- Problem: A refund whose outcome is unknown is declared NOT_APPLIED and its balance freed on one fetch showing the old total, with no minimum age and no stated client timeout. If the first refund lands after that fetch and the owner has issued a new one, both go out: a doubled partial refund that cannot be undone (no refund id, no idempotency).
- Evidence: PLANS/P08-CONTRACT.md:252 "total equals before -> failed with NOT_APPLIED (the owner may make a new refund)"; :222 reclaims "in-flight refunds older than 60 seconds"; :350 refund-recheck runs fetchPayment + refund_settle at any age (seconds after a timeout); no HTTP timeout appears in section 1 or 7, so a refundPayment call can still be in flight when the reconcile closes its row; :249 does not say what refund_result does when a late 200 arrives for a refund already `failed`. artifacts/acceptance/P08/moyasar-docs-2026-10-02.md:54 "Refund timing is not documented", :60 no idempotency for refunds.
- Correction: (a) State one client timeout for every Moyasar call, e.g. AbortSignal.timeout(10_000) as in supabase/functions/_shared/email.ts:109 and turnstile.ts:84, strictly below the 30 s and 60 s reclaim ages. (b) refund_settle answers NOT_APPLIED only when the refund row is at least 15 minutes old; before that `total = before` leaves it `uncertain`; refund-recheck obeys the same rule. (c) refund-create fetches the payment first and passes the fetched `refunded` to refund_request, which refuses (PROVIDER_TOTAL_UNRECONCILED) when it differs from the attempt's confirmed refunds, so a late-landed earlier refund is seen before a new one leaves. (d) Define refund_result on a refund that is no longer in flight: no state change, owner_alert, never a silent success or a raise. Add an emulator fault mode `commit_after_delay` and a test for it.

### A-PB-02 [high] 6 refund_request, refund_result, refund_settle, refund_record_external; apply_verified_payment (not_paid)
- Problem: The refund confirmation rule compares the provider total to `provider_refunded_before`, copied from a cached column that can be stale or overwritten. One mismatch leaves the refund `uncertain` forever, and that in-flight row blocks every later refund and refund_record_external on the payment: a state that cannot be left.
- Evidence: P08-CONTRACT.md:246 "provider_refunded_before = attempt.provider_refunded_halalas"; :202 not_paid: "Nothing changes except fetched_at and provider_refunded_halalas" with no check that the payment is the attempt's own. Documented case: invoice with payment p1 failed then p2 paid; the p1 failed-event retry arrives up to 3 h 41 min later (:62 retry schedule), settlePayment(p1) writes p1.refunded = 0 over the paid attempt's total. The next refund of amount a gets total = R + a, not 0 + a. :252 "anything else -> stays uncertain, TOTAL_MISMATCH"; :255 record_external needs "no refund in flight"; :166 one in-flight refund per attempt. Same dead end after a dashboard refund whose payment_refunded webhook was not received (reconcile never re-fetches a paid attempt, :222).
- Correction: apply_verified_payment writes provider_refunded_halalas only when p_payment.id equals the attempt's provider_payment_id (and in the `paid` branch, which :205 omits). refund_request takes the freshly fetched total (PB-01 c) as provider_refunded_before instead of the cached column. Give TOTAL_MISMATCH an exit: refund_record_external is allowed when the only in-flight refund is `uncertain` with TOTAL_MISMATCH; it closes that refund as `failed` (SUPERSEDED) and records one unallocated refund of (fetched total - confirmed refunds), so the ledger equals the provider's total whichever refund actually landed. Test: failed sibling event after a partial refund, then a second refund.

### A-PB-03 [high] 7 invoice step (startPayment); 6 payment_attempt_begin, payment_attempt_created, payment_reconcile_claim

### A-PB-04 [high] 7 invoice step, step 2; 2 consequences (uncertain creation); 8 emulator
- Problem: The uncertain-creation resolution trusts the list filter: "one match" is whatever GET /invoices?metadata[attempt_id]= returns. The contract itself lists metadata on creation and its filter as unconfirmed; if the real API ignores the filter, the list is every invoice, so a foreign invoice can be bound to the attempt, or (two or more rows) the case is undefined and the attempt stays `uncertain`. The emulator only implements the favourable behaviour, so neither branch the contract names can be tested and the sandbox move would need code.
- Evidence: P08-CONTRACT.md:315 "one match -> payment_attempt_created and return its URL"; :88 "If the provider did not keep the metadata the listing finds nothing" (assumes an unknown filter returns nothing); :73 the API reference omits metadata on create; :93 lists it to confirm; :365 emulator stores metadata and filters by it; :375 config has no switch for it (only refuseSecondRefund). payment_attempt_created has no defined answer when the listed invoice id already belongs to another attempt (provider_invoice_id unique, :152).
- Correction: The client matches on the returned objects, not on the filter: an invoice counts only when invoice.metadata.attempt_id equals the attempt id and its amount and currency equal the attempt's. Zero such invoices in a good answer -> abandoned (safe: that URL was never delivered). More than one -> stays `uncertain`, owner_alert. A unique violation in payment_attempt_created answers INVOICE_CONFLICT, never a 500. Emulator config gains `dropInvoiceMetadata` and `ignoreMetadataFilter`, each with a test; the runbook states that a 400 on `metadata` at creation is the one outcome that needs a code change.

### A-PB-08 [medium] 6 apply_verified_payment; 2 consequences; 6 reconciliation_list
- Problem: A paid payment that later becomes `voided` (a dashboard action, documented within about two hours) or changes status in any way other than a refund total produces `not_paid`, "nothing changes": the order stays paid, entitlements stay granted, statistics count money that went back, and refund_record_external cannot record it because the `refunded` total did not rise.

### A-PB-09 [medium] 7 checkout cancel; 8 emulator cancel route; 6 payment_reconcile_claim, payment_check_begin

What PUT /invoices/:id/cancel answers for a paid, expired or already-canceled invoice is not documented (it may be a 4xx); that case has no branch, so a crash between the provider cancel and the order cancel leaves a buyer who can neither pay nor cancel until the hold ends. Keep a cancelled or expired attempt that has an invoice id claimable by the reconcile until invoice_expires_at + 10 minutes, and say that payment_check_begin and payment_callback_begin return a check for any attempt with an invoice id that is not `paid` or `review`.

### A-PB-15 [low] 7 invoice step (expired_at); 6 payment_attempt_created
- Problem: expired_at is sent as the SQL timestamp string and the provider's echo is never checked. If Moyasar rejects the format, or stores another expiry or none, the attempt's invoice_expires_at (which drives when polling stops) no longer matches the invoice.
- Evidence: P08-CONTRACT.md:316 `expired_at: expiresAt`; :193 payment_attempt_created takes no expiry; :225 the attempt is closed from invoice_expires_at; :55 only "ISO 8601" is documented.
- Correction: The client sends new Date(expiresAt).toISOString() and compares the 201 reply's expired_at with it (one-second tolerance); on a difference it cancels the invoice and closes the attempt `failed` with last_error EXPIRY_MISMATCH. The emulator echoes expired_at and has a config switch to drop it.

## Lens B: money and concurrency (contract sections 3, 4, 6, 11; checkpoint 1, read-only)
Verdict: audit_failed

### B-MC-01 [critical] 3 Refund states (fold of 'requested' into 'submitting'); 6 refund_settle, refund_result, payment_reconcile_claim; 7 refund-recheck
- Problem: refund_settle marks an in-flight refund failed (NOT_APPLIED) and frees the balance whenever one fetch shows the provider total unchanged, but 'submitting'/'uncertain' cannot tell 'the call never left' from 'the call is still executing at the provider'. A refund that timed out and lands after that fetch is recorded failed, the owner is told to make a new one, and the buyer is refunded twice.
- Evidence: PLANS/P08-CONTRACT.md:120 claims settling by the total 'is safe whether or not the call left'; :252 'total equals before -> failed with NOT_APPLIED (the owner may make a new refund)'; :350 refund-recheck = fetchPayment + refund_settle with no age floor (the owner can press it seconds after a timeout); :222 the job's only guard is 'older than 60 seconds' and no client timeout is stated anywhere in section 7; :249 refund_result does not say what a late 'succeeded' does to a row that is no longer in flight. The emulator (:375) has 'timeout' and 'drop_after_commit' but no fault where the change is applied after the caller gave up.
- Correction: Enforce the floor inside refund_settle, not in its callers: 'total equals before' leaves the row uncertain until the row is older than a stated window far above the stated refund-call timeout (for example 10 s timeout, 15 min window, two unchanged fetches); only then NOT_APPLIED. refund_result and refund_settle act only on in-flight rows; a provider total later equal to before + amount for a failed/NOT_APPLIED row reopens it as succeeded (and blocks new refunds until reconciled). Either keep 'requested' (row written, call not yet started) apart from 'submitting' (set immediately before the call) so a crash-before-call row can fail at once, or keep the fold with the window. Add an emulator fault 'apply_after_timeout' and a test: timeout, immediate recheck, late application -> one refund, never 'failed'.

### B-MC-02 [high] 6 refund_request; 7 admin refund-create
- Problem: The admin action is written as refund_request, then refundPayment, then refund_result with no branch on the SQL answer. A retried or double-clicked request with the same idempotency key gets state 'duplicate' and, built as written, calls the provider again: a second real refund, because Moyasar has no refund idempotency.
- Evidence: PLANS/P08-CONTRACT.md:246 'The same key and hash answers the stored refund (state:'duplicate')'; :349 'refund_request; refundPayment(providerPaymentId, amount); refund_result'; :54 'Idempotency exists only for payment creation ... Nothing is documented for ... refunds'.
- Correction: State it in both layers: the provider is called only when refund_request answers state 'new'. 'duplicate' answers the stored refund's status and amount (no providerPaymentId) and the function returns it without any provider call, including when the stored row is still submitting (settlement is left to refund_settle). Test: the same key twice in parallel and in sequence -> exactly one refund call in the emulator's call log.

### B-MC-03 [high] 6 refund_request, refund_result, refund_settle, refund_record_external; 4 payment_attempts.provider_refunded_halalas
- Problem: An uncertain refund with TOTAL_MISMATCH is a state with no exit, and it blocks every other refund of the payment. It is reached whenever the provider total moved for another reason (a dashboard refund before or during the call) or the cached 'before' was stale.
- Evidence: PLANS/P08-CONTRACT.md:252 'anything else -> stays uncertain, TOTAL_MISMATCH, owner alert' (no further move exists); :246 REFUND_IN_FLIGHT refuses a new refund and 'provider_refunded_before = attempt.provider_refunded_halalas' is a cached value, not a fetch; :255 refund_record_external requires 'no refund in flight' and is not said to update attempt.provider_refunded_halalas; :202 the not_paid path overwrites provider_refunded_halalas from a fetch made outside any lock, so a delayed webhook can write an older total over a newer one. Example: dashboard refund 30 unrecorded, refund-create 50 -> provider total 80, expected 50 -> uncertain forever. The refunds table (:166) has no next-check column, so the job also fetches this row every minute forever (:222).
- Correction: (a) refund-create fetches the payment first and passes the fresh total to refund_request, which stores it as 'before' and answers EXTERNAL_REFUND_UNRECORDED when it differs from the attempt's confirmed refunds (the owner records the external refund first). (b) Every write of provider_refunded_halalas is greatest(old, new); refund_record_external writes it too. (c) Add an owner action with fresh TOTP (refund-resolve / SQL refund_resolve) that closes a TOTAL_MISMATCH row from a fresh fetch under the order and attempt locks: total >= before + amount -> this refund succeeded and the surplus is recorded as a provider_dashboard refund in the same transaction; before < total < before + amount -> this refund failed and the difference is recorded as external. (d) A TOTAL_MISMATCH row stops being polled and waits for the owner.

### B-MC-04 [high] 3 Payment attempt 'review'; 4 payment_attempts; 6 apply_verified_payment (SECOND_PAYMENT, review), payment_attempt_begin, refund_request
- Problem: A second payment on a paid attempt has nowhere to be recorded: the attempt holds one provider_payment_id and stays 'paid', so the second payment's id and amount are in no ledger row, cannot be refunded through refund-create or seen by refund_record_external, and are missing from statistics. For the other review reasons the contract never says the reviewed payment's id is stored, and a buyer can open a new invoice on an order whose money already sits in review.
