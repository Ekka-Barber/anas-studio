- **Kind:** product-defect; money, permissions or a migration: false; visual only: false

**Root cause.** restore-check has only one way of keeping the scratch stack on loopback, and that way does not work on the machine the rehearsal has to run on. The Supabase CLI 2.106.0 publishes every port with a host port and no host IP, and no setting or environment variable changes that (checked in its v2.106.0 source). So restore-check relies entirely on the bridge default com.docker.network.bridge.host_binding_ipv4=127.0.0.1. It sets that default on the network it creates first (scripts/restore-check.mjs:233) and hands the network to `supabase start --network-id` (:621). On Docker Desktop 4.91.0 (engine 29.8.0) that option has no effect. Docker Desktop's backend opens the Windows-side listener under its own 'Port binding behavior' policy, and the default is 'Open (Default)' (ports 'available on the local network'). A binding with an empty host IP therefore lands on 0.0.0.0 and [::] whatever the network says. The orchestrator reproduced this with a plain docker run, without the CLI. An explicit 127.0.0.1 is honoured. So `docker port` printed 0.0.0.0:55322 and [::]:55322, and assertLoopbackOnly (:250-263) refused before anything was restored. That refusal was correct and the guard must stay. The defect is the binding mechanism, and the product's claim that the network is bound to 127.0.0.1 (restore-check.mjs:23-27, :226-229; docs/operations.md:1951-1953). The claim holds on a Linux engine but not on Docker Desktop at its default settings, which is the owner's machine, where the rehearsal must run (docs/operations.md:1986-1995; PLANS/ISSUES.md I53 (3)). The stand-in suite runs on POSIX only (tests/unit/restore-check.test.ts:233, :281) and proves the decision, not Docker's behaviour, as I53 (3) warned. This is not an environment problem: the machine is at Docker Desktop's defaults, not misconfigured, and a fix exists in the product. Every orchestrator claim I could check holds. Its checks missed two things: Docker Desktop's own port policy, and the DOCKER_HOST route into the CLI (see fix).

**Intended by.** n/a: not a test-defect. No recorded change replaced what the battery expects. The refusal is restore-check's intended guard (scripts/restore-check.mjs:260-263; PLANS/ISSUES.md:73, I53 (3)), and it worked; the binding mechanism under it is what fails on this machine.

**Fix.**

A product-side fix exists. It keeps the guarantee and removes this cause on this machine. Size: medium, about 200-250 lines with tests and docs, one new file; no migration and no money path. The rest of the rehearsal (restore, uploads, cron) has never run on this machine, so only a re-run of work/scripts/battery-backup.sh proves a pass.

(1) New scripts/lib/docker-loopback-relay.mjs: a small in-process Docker API relay.
- restore-check starts it just before `supabase start` and closes it when start returns, and again in cleanup.
- It listens on an endpoint private to the user: a named pipe \\.\pipe\anasaq-restore-<random> on Windows, a unix socket in a fresh 0700 temp dir on POSIX. Never TCP: a Docker API on a loopback TCP port is reachable by any local process.
- It forwards every request byte for byte to the endpoint that plain `docker` uses: DOCKER_HOST if set, otherwise `docker context inspect --format {{.Endpoints.docker.Host}}`. Chunked streams and `Upgrade: tcp` hijacks (exec, attach) pass through unchanged.
- It changes one thing. In `POST /containers/create` (versioned or not), every HostConfig.PortBindings entry with an empty HostIp gets "127.0.0.1", and Content-Length is recomputed. An entry that names any other address is answered with a 4xx, so the CLI fails closed.

(2) Start the CLI through the relay.
- restore-check.mjs:621 runs `supabase start` with env {...process.env, DOCKER_HOST: npipe:////./pipe/... or unix://...}.
- The CLI takes its endpoint from DOCKER_HOST (docker.go:43, :51), and the 2.106.0 shell passes the environment and --network-id through (go-proxy.layer.ts:204-207). The CLI's own connections stay on 127.0.0.1 (misc.go:305-311).
- Docker Desktop honours an explicit 127.0.0.1 in both docker port and the Windows listener (backup-bindcheck.txt:18-20, :28).
- Keep createLoopbackNetwork and --network-id: they are still right on a Linux engine.

(3) Widen assertLoopbackOnly (:250-264) from the db container to every container labelled com.supabase.cli.project=anasaq-restore-check.
- List them with `docker ps -a --filter label=... -q`, then run `docker port` on each. Require at least one binding overall and every binding on 127.0.0.1.
- Keep reading through plain docker, never through the relay. The guard is not loosened.
- Why it is needed: once the binding is set per request, the reasoning at :248-249 (the db container stands for them all) no longer holds. Kong on 55321, with the CLI's default secret key, reaches the same restored rows. Today only the battery's probe looks at the other containers, and it runs after the restore (battery-backup.sh:59-64, :89 against restore-check.mjs:630, :633).

(4) Tests.

(5) Docs: update docs/operations.md:1951-1956 and :1986-1995, and PLANS/ISSUES.md I53 (3), to say how the binding is now made and that Docker Desktop ignores the network option.

## The refuter (Opus 5.5, effort max, read-only)

- **Upheld:** true

Upheld: product-defect, and the cause holds. I re-read every cited line and checked the gaps myself. The guard refused after a successful `supabase start`, before any restore, and the cleanup held. The only loopback mechanism, the network default (restore-check.mjs:233, handed over at :621), is not applied on this Docker Desktop 4.91.0 / engine 29.8.0: a plain `docker run` reproduces it without the CLI, and an explicit 127.0.0.1 is honoured. The CLI 2.106.0 has no host-IP setting. Added confirmations: (1) the stable 2.106.0 release ships the legacy shell, whose `start` only proxies to supabase-go with --workdir and --network-id, so the Go bindings are what ran; (2) upstream moby docker-v29.8.0 applies host_binding_ipv4 inside the engine, so the design holds on a vanilla Linux engine and the loss is Docker Desktop's; (3) Supabase's own guide recommends exactly this design, which the first auditor left unconfirmed; (4) docker/cli v28.5.2 lets DOCKER_HOST override DOCKER_CONTEXT and currentContext, so the relay route is real. Windows with Docker Desktop is the stated target (operations.md:1988, S.md:77), so this is a product defect, not an environment one.

Not proven, and not material: that Docker Desktop's 'Port binding behavior: Open (Default)' policy is what drops the default. `docker port` and `docker inspect` show the engine's own record. The evidence shows that something on Docker Desktop's path drops the network default, not which component. The setting's text speaks of ports in general and never of a network's default. That the machine is 'at Docker Desktop's defaults' was not checked either (settings files are off limits). Step (5)'s docs should say only that Docker Desktop does not apply the network's default binding.

Fix: the right remedy in kind. I found no cheaper product-side remedy that keeps the guarantee: the CLI has no host-IP key, and daemon "ip", default-network-opts and the firewall fail for the reasons the verdict gives. The owner-side setting stays unverified and hidden behind a feature flag. But the fix must not be dispatched as written:
(a) Blocking: `supabase()` is spawnSync (:133-135), which blocks restore-check's event loop for the whole start. An in-process relay on the main thread could not serve one request, so the CLI would hang until the 600 s timeout. Host the relay in a worker_threads Worker, which keeps spawnSync and today's Ctrl+C order, or use an async spawn whose SIGINT path waits for the child before cleanup. Test it with a start stand-in that really sends POST /containers/create through DOCKER_HOST to a fake upstream; the proposed 'gets DOCKER_HOST' check passes with a dead relay. Run the relay's own test over a real named pipe so it runs on Windows, where every stand-in case is skipped.
(b) Step (3) loosens the S-A3 fix: 'at least one binding overall' over a label-only list drops the db container's own non-empty rule (:257-259), and skips the db container entirely if it lacks the label. Keep the db check by name with its rule, require a Kong binding too, and add every container found by label or by name (as battery-backup.sh:60-64 does), each on 127.0.0.1.
(c) Fail closed on more cases: refuse PublishAllPorts=true, NetworkMode host, and any create body the relay cannot parse (chunked or bad JSON) instead of forwarding it unchanged.
