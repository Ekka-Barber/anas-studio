UI bug found and fixed: CollectionForm rendered both the fields <div> and
<VersionHistory> as siblings keyed by the same value (key={loadGeneration}).
React requires unique keys among all direct children of one parent, not just
within one mapped list; the collision ("Encountered two children with the
same key" in the console) made React duplicate DOM subtrees after a second
save/publish/schedule cycle (observed: label/input counts for an unrelated
field doubling to 4), which silently broke later locator-based assertions
(stale values, mis-clicked buttons) with no visible error. Fixed by giving
VersionHistory a distinct key (`history-${loadGeneration}`). Caught while
diagnosing two cms.spec.ts e2e failures (room movement reorder and the
conflict test) that reproduced identically across a from-scratch dev-server
restart, ruling out HMR flakiness; a standalone repro script confirmed the
duplicate-key warning and the DOM duplication directly.

Disclosed, not fixed (forbidden path, src/app/(public)/started/page.tsx):
that page renders reels from a hardcoded id array (ART), independent of
room.media.reels/its hidden flag, so hiding a reel via the admin has no
visible effect on /started's rendered <video> elements today. The room e2e
test's hidden-reel assertion (44-animated-kitchen's poster/source absent) is
consequently vacuous, not a meaningful regression check, until that page is
fixed to read room.media.reels.
