P00 task 4 — cache interception experiment
============================================

Source consulted (fetched live in this task, not recalled):
  https://opennext.js.org/cloudflare/caching
  Fetched via `curl -sL` into the scratchpad, tags stripped with node, read in
  full. Relevant quotes:

  "Everything in this page only concerns SSG/ISR and the data cache, SSR route
  will work out of the box without any caching config."

  "You can also enable cache interception, to avoid calling the NextServer and
  thus loading the javascript associated with the page. It can slightly improve
  cold start performance for ISR/SSG route on cached routes. As of now, cache
  interception does not work with PPR and is not enabled by default."

  "SSG site — If your site is static, you do not need a Queue nor a Tag Cache.
  You can use a read-only Workers Static Assets-based incremental cache for the
  prerendered routes":

    import { defineCloudflareConfig } from "@opennextjs/cloudflare";
    import staticAssetsIncrementalCache from "@opennextjs/cloudflare/overrides/incremental-cache/static-assets-incremental-cache";

    export default defineCloudflareConfig({
      incrementalCache: staticAssetsIncrementalCache,
      enableCacheInterception: true,
    });

  "Workers Static Assets: A read-only store for the incremental cache, serving
  build-time values from Workers Static Assets. Revalidation is not supported
  with this cache."

  Both the `enableCacheInterception` option and the
  `@opennextjs/cloudflare/overrides/incremental-cache/static-assets-incremental-cache`
  module were cross-checked against the installed package
  (@opennextjs/cloudflare 1.20.6, node_modules/@opennextjs/cloudflare/dist/api/
  config.d.ts and .../overrides/incremental-cache/static-assets-incremental-cache.d.ts)
  before use — the doc's names match the installed version exactly.

What changed
------------
`open-next.config.ts`: replaced bare `defineCloudflareConfig()` with the doc's
"SSG site" recipe — `incrementalCache: staticAssetsIncrementalCache` and
`enableCacheInterception: true` — plus a rewritten comment. The prior comment
conflated public-page caching with database query caching; the new one states,
citing the doc verbatim, that this is SSG/ISR-only and that SSR routes
(admin, /api/health, and any authorization/inventory read) are unaffected and
keep hitting the database on every request.

No change to `wrangler.jsonc` bindings — no R2/D1/Durable Object queue or tag
cache was added, because nothing in this repo currently calls `revalidateTag`,
`revalidatePath`, or uses time-based ISR. That is out of scope for this task
and left to P01/P04.

What is still unproven
-----------------------
This is a local Miniflare/workerd preview, not a Cloudflare deployment. It
shows that cache interception activates for the one static route and does not
touch dynamic routes, and that the bundle still builds and dry-run-bundles
cleanly. It does NOT show:
  - the real cold-start / warm CPU time on Cloudflare's edge,
  - whether cache interception actually pulls the public route's *measured*
    CPU time under the Workers Free 10 ms limit (the P00 baseline measured
    20.5 ms p50 against calling the Next server; interception skips that
    server call entirely for a cache hit, which plausibly helps, but the
    magnitude is not measured here),
  - `Worker Startup Time`, which wrangler only reports on a real deploy.

These remain open until the owner runs the deploy script below and the
orchestrator measures the deployed Worker.

## Public JS budget, corrected measurement

Command run (inside the already-running container, matching the repo's own
scripts/check-budgets.mjs, copied into the container since /app is not a
bind mount — `docker cp scripts/check-budgets.mjs anasaq-bundle:/app/scripts/check-budgets.mjs`):

    docker exec anasaq-bundle sh -lc "cd /app && node scripts/check-budgets.mjs"

Old figure (before this fix): 980.4 KiB gzip, summing all 63 files under
`.next/static/chunks` including the Payload admin bundle — a false red,
never downloaded by a public visitor.

New figure: the script now parses `.next/server/app/index.html`, extracts
the `<script src="/_next/static/chunks/*.js">` tags it actually contains,
and gzips only those files on disk.

  - Homepage script count: 7 total `<script src>` tags referencing
    `/_next/static/chunks/*.js`. One of them (`0cz1d0mv5g_q7.js`, 112,594
    bytes raw / 39,496 bytes gzip) carries a `noModule` attribute — the
    legacy pre-ES-module fallback bundle modern browsers never fetch.
  - Polyfill: EXCLUDED. The script detects `noModule=""` on the tag and
    skips that chunk, per the task's instruction to distinguish it.
  - Sum of the remaining 6 modern-path scripts: 134,843 bytes gzip =
    131.6 KiB, computed by the script (`gzipSync` via Node's zlib).
  - Cross-check: independently gzipped each of the 7 referenced chunks with
    `gzip -c | wc -c` inside the container. The 6 non-polyfill scripts sum
    to 134,843 bytes (131.6 KiB), matching the script's own figure. Adding
    the polyfill's 39,496 bytes gives 174,339 bytes = 170.3 KiB — this
    matches the task's own prior manual estimate of "170.3 KiB / 7 scripts"
    exactly, confirming that estimate included the polyfill.

Actual output:

    check:budgets
      worker upload:        25338.5 KiB  (limit 65536.0 KiB)
      worker gzip (info):    5611.2 KiB  (no Cloudflare limit; informational)
      public JS gzip:        131.6 KiB  (budget 150.0 KiB, 6 homepage scripts, 1 nomodule polyfill excluded)
    EXIT: 0

Result: PASS (131.6 KiB against the 150 KiB budget), not the FAIL the task
predicted. This is a genuine result, not a forced pass — the budget constant
(`PUBLIC_JS_GZIP_BUDGET_BYTES`) was not touched, and the polyfill exclusion
was explicitly permitted by the task ("skip the nomodule legacy polyfill if
you can distinguish it"). The task's predicted ~170 KiB / FAIL figure was
itself the 7-script sum with the polyfill still counted; once the polyfill
correctly drops out (as modern browsers never fetch it), the measurement
comes in under budget. Flagging this explicitly since it contradicts the
task's stated expectation — reporting the real measured number, not the
predicted one.

NOT PROVEN BY THIS MEASUREMENT
- p99 31.1 ms still exceeds the 10 ms limit. The typical request now fits with
  margin; roughly one request in a hundred does not. Cloudflare documents
  tolerance for a Worker that infrequently runs over, which is a materially
  different position from the earlier p50 being over, but it is tolerance, not
  compliance.
- The scheduled path is untouched. Cache interception cannot help it: a real
  cron delivery measured 91 ms CPU and runs the full Next pipeline.
- The 600.692 second scheduled invocation found in raw logs is still unexplained.
- R2 round trip with unauthorized denial, real cron content write, and
  authenticated hosted CRUD remain unrun.
