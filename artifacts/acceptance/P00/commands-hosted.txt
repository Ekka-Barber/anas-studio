## Step 2 — seed the single owner before the Worker is reachable

First attempt: `payload run <script>` with the script dynamically
`import()`-ing `src/payload.config.ts` (as `payload migrate`/`generate:types`
do internally). This did NOT work: the dynamic import silently triggered
`process.exit(0)` with no thrown error and no output past "about to import
config" — confirmed with `process.on('exit'|'unhandledRejection'|
'uncaughtException', ...)` listeners that only the `exit` event fired, code 0.
Root cause not fully isolated; the working theory, from a related symptom
seen one step later, is `@opennextjs/cloudflare`'s `getCloudflareContext()`
raising an unhandled rejection during a nested dynamic import outside a
request/dev-server context, which `payload run`'s bare Node process does not
tolerate the way `next dev`'s long-lived server does. This is a real,
reproducible defect in how this repository's own tooling composes with
`payload run`, not a hosted-half result — reported as a finding, not
worked around by relaxing anything.

Working approach: ran `pnpm dev` on the Windows host directly against the
hosted database (DATABASE_URL, same session endpoint; `next dev` loads `.env`
itself), and used Payload's native `POST /api/users/first-register` endpoint
— the exact same code path the Worker's `/admin/create-first-user` UI calls —
so the seeded owner is byte-for-byte what native bootstrap would have
produced, only run from a private localhost server instead of the public
Worker.
