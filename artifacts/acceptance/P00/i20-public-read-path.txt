## 2. A real leak caught while regenerating `cloudflare-env.d.ts`

`pnpm cf-typegen`'s actual script (`package.json`) is
`wrangler types --env-interface CloudflareEnv cloudflare-env.d.ts`, with no
`--env-file` flag. Run exactly that on this machine and it pulls in every key
name from this machine's local `.dev.vars`/`.env` discovery — not values, but
names — into the *committed* type file: `CLOUDFLARE_API_TOKEN`,
`SUPABASE_DB_PASSWORD`, `SENTRY_SETUP_RUN_CODE`, `UPTIMEROBOT_API_KEY`,
`P00_OWNER_PASSWORD`, and more, none of which are declared in `wrangler.jsonc`.
Confirmed by actually running it and reading the diff, not assumed. The
previous committed file's own header comment ("run with an empty --env-file
so that local .env names are not declared as Worker bindings") records that
whoever generated it before hit the same thing and worked around it by hand;
`package.json`'s script itself was never fixed and is not in this task's
write scope (shared manifest). Regenerated instead with:

  wrangler types cloudflare-env.d.ts --env-interface CloudflareEnv \
    --env-file=<path to an empty scratch file>

Result: only `SITE_URL` and `ADMIN_URL` appear (both declared in
`wrangler.jsonc`'s `vars`), matching what a clean build should produce. The
leading comment line was hand-edited afterward to remove the session-specific
scratch path and restate the reason, mirroring the prior file's own comment
style. **Remaining risk, flagged for the orchestrator:** `pnpm cf-typegen` as
written in `package.json` is a live footgun — anyone who runs it bare on a
machine with a populated `.dev.vars`/`.env` will silently commit local secret
*names* into a tracked file. Fixing `package.json`'s script is outside this
task's allowlist.

## 3. A real bug caught by building, not assumed: `generateStaticParams`

First `pnpm build:worker` (before adding `generateStaticParams`) produced:

  Route (app)
  ...
  └ ƒ /probe/[id]

`ƒ` = "server-rendered on demand" — plain SSR, not ISR. Read
`.next/prerender-manifest.json` after that build: `dynamicRoutes: []` — the
probe route was NOT in it. Cross-checked against
`node_modules/@opennextjs/aws/.../core/routing/cacheInterceptor.js`'s `isISR`
check, which only intercepts a path listed in `PrerenderManifest.routes` or
matching `dynamicRoutes`' regex. Left as originally written, the R2/D1 cache
would never have been consulted for this route at all — every request would
still boot Payload, the exact CPU cost I20 exists to fix, silently
unfixed.

Root cause: in App Router, a dynamic segment page with no
`generateStaticParams` at all is fully dynamic by default; the manifest entry
that makes ISR-with-fallback caching possible only appears once
`generateStaticParams` is defined, even if it returns `[]`. Added
`export async function generateStaticParams() { return [] }` to
`src/app/(public)/probe/[id]/page.tsx`. Rebuilt:

  Route (app)
  ...
  └ ● /probe/[id]

`●` = SSG ("uses generateStaticParams"). `prerender-manifest.json` afterward:

  "dynamicRoutes": { "/probe/[id]": { "fallback": null, ... } }

`fallback: null` is Next's "blocking fallback" — first visit to any id
renders on demand and is then cached; nothing is pre-rendered at build time.
Confirmed working end to end in section 5.

## 4. A real bug caught by testing, not assumed: `revalidateTag`'s new required second argument

`pnpm typecheck` failed first:

  src/app/api/revalidate/route.ts(51,35): error TS2554: Expected 2 arguments, but got 1.

`node_modules/next/dist/server/web/spec-extension/revalidate.d.ts`:
`revalidateTag(tag: string, profile: string | CacheLifeConfig): undefined` —
Next 16 made the second argument required (a "cache life" profile). The
runtime implementation
(`node_modules/next/dist/server/web/spec-extension/revalidate.js`) still
warns-and-continues without it ("`revalidateTag` without the second argument
is now deprecated, add second argument of `max` or use `updateTag`"), so this
was a real behaviour change to account for, not just a type error.
`updateTag` is not usable here — "can only be called from within a Server
Action", and this is a Route Handler.

First fix: `revalidateTag(tag, 'max')`, following the deprecation warning's
own suggestion. Typechecked and built clean, so it shipped to the first local
proof — and failed the proof. Editing a published document's title directly
in Postgres, calling `POST /api/revalidate` with the correct secret, then
re-requesting the page still returned the *old* title on the very next
request (`x-opennext-cache` header absent, meaning it fell through to the
real Next.js server, which then still served stale content).

Root-caused by reading, not guessing:
`node_modules/@opennextjs/cloudflare/dist/api/overrides/tag-cache/d1-next-tag-cache.js`'s
`hasBeenRevalidated`: `if (expire != null) return expire <= now && expire >
lastModified`. `'max'` writes a `stale`/`expire` window roughly a year in the
future (`next/dist/server/config-shared.js`'s `cacheLife.max`:
`revalidate: 30d, expire: 365d`), so `expire <= now` is false — the tag cache
answers "not revalidated" even though it was, and the entry only qualifies
for the *soft* `isStale` (stale-while-revalidate) path, which tries to queue
a background refresh via `globalThis.queue.send(...)`
(`cacheInterceptor.js`) — this app has no queue configured (by design, see
section on `open-next.config.ts`), so that call has nothing to do and the
page keeps serving the old value with no way to catch up.

Fix: `revalidateTag(tag, { expire: 0 })`. `@opennextjs/aws`
`adapters/cache.js`'s own `revalidateTag` comment: "Immediate expiration,
default behavior before next 16, now only with `{expire: 0}`" — this is the
literal replacement for the pre-Next-16 default (immediate, hard, no-queue
invalidation), not `'max'`, which is a different, SWR-flavoured semantic the
deprecation message also offers but that does not fit an app with no queue.
Re-tested (section 5): the very next request after revalidate now shows the
new title.

## 6. What local wrangler dev does and does not prove

Proves: the whole on-demand invalidation loop is wired correctly end to end —
R2 incremental cache, D1 tag cache, `revalidateTag`/`revalidatePath`, the
Worker's own routing gate (`/admin` redirect, `/api/*` refusal), and the
access-control change on `RuntimeProbe.read`, all against the real built
`.open-next/worker.js` artifact run by `workerd` (the real Workers runtime),
not `next dev`.

Does not prove: real R2/D1 network latency or quota behaviour (local
simulation has neither), real Hyperdrive pooling behaviour (Hyperdrive
itself is bypassed locally in favour of a direct Postgres connection string —
this was already true and already documented before this task), CPU time on
a cache hit under production's 10 ms Free limit (not measured here — that is
hosted-half work, blocked the same way the rest of P00's hosted proofs are:
no deploy performed), the real `opennextjs-cloudflare deploy`/`upload`
`populateCache` step against real R2/D1 (only the `local` target was
exercised, never `remote`), and whether Automatic Cache Purge or a custom
domain change any of this once `anas.studio` is a real Cloudflare zone
(deliberately not configured — see `open-next.config.ts`'s comment).

## R2.4 — safe `cf-typegen`, proven on both hosts

Root cause (already described in Round 1 section 2): the old script,
`wrangler types --env-interface CloudflareEnv cloudflare-env.d.ts`, has no
`--env-file`, so wrangler auto-discovers this machine's `.dev.vars`/`.env`
and declares every key name it finds as a Worker binding in the committed
type file.

Fix: added a tracked, always-empty file `wrangler-empty.env` (not `.env.*`,
so `.gitignore`'s `.env`/`.env.*` rule does not touch it — confirmed with
`git check-ignore -v wrangler-empty.env`, exit 1, not ignored) and pointed
`--env-file` at it explicitly:

  "cf-typegen": "wrangler types cloudflare-env.d.ts --env-interface CloudflareEnv --env-file=wrangler-empty.env"

Two real ordering bugs found and worked around while getting here, both
confirmed by running the exact command, not assumed:

- `--env-file` is an array-type wrangler flag. Placed *before* the positional
  output path (`--env-file=<path> cloudflare-env.d.ts`), it swallows the
  positional into itself — even with `=` syntax on the first value — and
  wrangler falls back to writing the default `worker-configuration.d.ts`
  instead, with garbage extra "keys" in the output (observed: literal `"0"`
  and `"1"` in the generated `ProcessEnv` type). Reproduced twice, once on
  each host.
- Fix is ordering, not syntax: the positional path must come *first* —
  `wrangler types cloudflare-env.d.ts --env-interface CloudflareEnv
  --env-file=wrangler-empty.env`. This is what shipped.

Proof, both hosts, both exit 0:

  Windows host (this machine's own real `.dev.vars`/`.env`, whatever it
  currently holds — not inspected, only relied on as a pre-existing fixture):

    $ pnpm cf-typegen
    exit 0

    interface __BaseEnv_CloudflareEnv {

  Linux container (`anasaq-bundle`), with a throwaway fixture `.dev.vars`

### Step 2 — publish through the real node-target hook, not SQL

"Don't use raw SQL" — used the Payload Local API directly instead, in a
disposable script (`tmp-publish-r2.ts`, written to the repo root only inside
the container so `node_modules` resolution worked, deleted immediately after,
never committed). Node's own native TypeScript stripping could not run it —
a real, separate finding:

  Error [ERR_MODULE_NOT_FOUND]: Cannot find module '/app/src/lib/db'
  imported from /app/src/payload.config.ts

Node 24's built-in TS support strips types but does not resolve TypeScript's
extension-less relative imports (`from './lib/db'`) the way a bundler does —
this project's source relies on that resolution throughout, same as the
`payload run` defect already recorded in `docs/runtime-spike.md`, but hit via
a different path this time. Worked around with `tsx` (already present as a
transitive dependency, `node_modules/.pnpm/tsx@4.22.4`, not top-level so
invoked via its `dist/cli.mjs` directly rather than `npx tsx`, which failed
to resolve a bin that isn't hoisted).

The script calls `getPayload({ config })` directly, then
`payload.update({ collection: 'runtime-probe', id, data: { _status },
overrideAccess: true })` — the same Local API shape the node admin's REST
handler ultimately calls, with `overrideAccess: true` standing in for an
authenticated admin session (the point of this proof is the collection hook,
not access control, which is already exercised elsewhere). Run with:

  RUNTIME_TARGET=node, PAYLOAD_SECRET (throwaway), ADMIN_URL (throwaway,
  http://localhost:3000 — required by payload.config.ts, never reached),
  CMS_DATABASE_URL -> p00-i20r2-pg, R2_ENDPOINT/R2_ACCESS_KEY_ID/
  R2_SECRET_ACCESS_KEY/R2_BUCKET_NAME (throwaway, matching the I19 precedent
  — uploads never exercised), SITE_URL=http://127.0.0.1:8787 and
  REVALIDATE_SECRET matching `.dev.vars` — both pointing at the running
  preview, so `notifyRevalidate` calls the real Worker.

This is what makes the hook real, not simulated: `isNodeRuntimeTarget()`
(`RUNTIME_TARGET=node`) is what makes `RuntimeProbe.ts`'s conditional
`hooks:` object non-`undefined` in the first place — the same module-load-time
switch the rest of this codebase already uses (`jobs.ts`'s `autoRun`,
`storage.ts`'s adapter choice).

### Step 3 — timing the hook's POST without touching committed source

The hook calls `notifyRevalidate` fire-and-forget (`void`, never awaited) —
correct per its own contract, but it means nothing in the normal call chain
reports how long the outbound POST took, and nothing should: the admin save
must return immediately regardless. Measured by temporarily wrapping
`globalThis.fetch` *inside the disposable script only*, timing exactly the
calls whose URL contains `/api/revalidate`, and giving the process 3 extra
seconds before exit so the un-awaited promise had time to actually finish
(otherwise `process.exit()` right after `payload.update()` resolves could
cut the in-flight request off — a real risk for a one-shot script that a
long-lived node admin process does not have).

  publish:            UPDATED ... status= published
                       REVALIDATE_HOOK_POST_MS 146 status 200
  unpublish (draft):  UPDATED ... status= draft
                       REVALIDATE_HOOK_POST_MS 55 status 200
  publish (again):    REVALIDATE_HOOK_POST_MS 44 status 200
  delete:              DELETED ...
                       REVALIDATE_HOOK_POST_MS 58 status 200

44–146 ms, same-container loopback HTTP the whole way (script -> preview
Worker), so this is a floor, not a production estimate — real network hops
(VM -> Cloudflare edge) are not represented. Well inside the 60-second P02
budget either way.

### Step 4 — does the cache actually flip, in both directions?

  After publish (step 2's first call):
    GET /probe/<id> (1st) -> 200, x-opennext-cache: (absent), body contains
      "فحص مسودة الجولة الثانية"
    GET /probe/<id> (2nd) -> 200, x-opennext-cache: HIT

  After unpublish:
    GET /probe/<id> (1st) -> 404, x-opennext-cache: (absent)
    GET /probe/<id> (2nd) -> 404, x-opennext-cache: HIT

  Republished, confirmed 200, then deleted:
    GET /probe/<id> after delete -> 404

**No fix was needed.** The cached 404 *was* correctly invalidated by the tag
on every transition (publish, unpublish, delete), on the first try, with the
code exactly as Round 1 left it. Root cause, read from source rather than
assumed: `src/app/(public)/probe/[id]/page.tsx`'s `unstable_cache(..., {
tags: [runtimeProbeTag(id)] })` call passes its `tags` option to the wrapper
unconditionally — the callback's return value (a document, or `null` on the
`NotFound` catch) has no bearing on which tag gets attached. Next's own
`getFetchCache`/`getIncrementalCache` (`@opennextjs/aws` `adapters/cache.js`,
already read in Round 1) key the *page's* Full Route Cache entry off the same
aggregated tag set regardless of whether that render produced a 200 or a 404
body. One tag, one id, covers both outcomes by construction — there was
never a separate "not-found" cache namespace to forget to tag.
