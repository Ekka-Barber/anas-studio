## 1. Method

`wrangler check startup` (docs:
https://developers.cloudflare.com/workers/wrangler/commands/workers/#check,
section "startup", dateModified 2026-09-22, fetched 2026-09-23 — this command
is real; it is not documented under a `wrangler check startup` heading
anywhere else, only under `check` > `startup`) builds the Worker, profiles a
fixed idle window with nothing sent to it, and reports "Active" CPU plus a
`.cpuprofile`. Per its own note: "measures performance of your Worker locally
... which has a different CPU than when your Worker runs on Cloudflare ...
results can vary widely." This is item (a): isolate startup / global-scope
evaluation.

For (b) lazy module loading on the first request and (c) the cache lookup
itself, `wrangler check startup` sends no request, so it cannot separate
them. Instead: `pnpm preview:worker -- --inspector-port 9230`, wait for
"Ready", then query `http://127.0.0.1:9230/json` for the
`webSocketDebuggerUrl` (`ws://127.0.0.1:9230/ws`) and speak the Chrome
DevTools Protocol directly — `Profiler.enable` / `Profiler.start`, one
`fetch()` to the running preview, `Profiler.stop`, save the `.cpuprofile`.
Attaching *after* "Ready" means global-scope evaluation has already run by
the time profiling starts, so this captures only what the first real HTTP
request itself does.

Node 24's native `WebSocket` client failed the handshake against this
specific server (undici's `failWebsocketConnection`, socket closed by the
peer mid-handshake, cause not fully root-caused); a raw `net.Socket` HTTP
upgrade to the same URL succeeded immediately (101 Switching Protocols,
valid CDP frames). Worked around with a ~130-line hand-rolled RFC 6455
client (`ws-client.mjs`, text frames only, extended-length frames handled,
scratch script, not part of the repo) rather than adding a dependency for a
one-off local measurement.

`.cpuprofile` self time was read from the `samples`/`timeDeltas` arrays
(the authoritative source per the Chrome DevTools protocol's own CPU profile
format), not the `nodes[].hitCount` field, which is coarser. Idle time and
V8-internal `(program)` time are reported separately from named JS
functions. Local sampling interval was requested at 50 microseconds
(`Profiler.setSamplingInterval`); actual inter-sample gaps were larger and
uneven, because most of the profiled window is the async wait on the local
R2/D1/Hyperdrive-over-loopback I/O the request makes, not CPU-bound work —
expected, and the reason idle time dominates every profile below. All
`.cpuprofile` files were deleted from the container at teardown (temporary,
not retained as evidence beyond the numbers below); `.cpuprofile` is JSON, so
the same file layout would be trivial to regenerate the same way.

Local and hosted CPU differ in absolute value (I20/I21 already state this);
everything below is a *relative*, same-hardware, same-container comparison
of one build against another, not a claim about hosted numbers, which were
already measured in I20/I21 and are not re-measured here.

module-load cost that I20/I21's hosted evidence says is already being
charged to the first request's CPU meter on real Workers (a fresh-isolate
cache HIT costs 17–46 ms hosted, vs 2–5 ms warm — that gap has to be paying
for *something* on the first request, and this local measurement boundary
was drawn on the wrong side of it for the static-import build).

## 3. Source read, to decide what to change (@opennextjs/cloudflare 1.20.6, @opennextjs/aws 4.1.4, installed)

- `.open-next/worker.js` (the `open-next-worker` alias target) is one
  bundled file containing the Next.js server, the cache interceptor, the D1
  tag cache, and Payload's own dependency tree (compiled twice — see I20's
  §5, unresolved, not re-investigated here). Everything in it that is
  reached via a *static* `import` at the top of `worker-entry.ts` becomes
  part of the same single-file esbuild bundle's top-level, executed in
  module-evaluation order — i.e. at isolate startup, regardless of which
  route a request hits.
- `node_modules/@opennextjs/aws/dist/core/routing/cacheInterceptor.js`
  (referenced by `open-next.config.ts`'s own comment, re-read here): a cache
  `HIT` answer still has to reach this file's `cacheInterceptor` function,
  which needs the built route/prerender manifest and the R2/D1 override
  modules already initialized — there is no cheaper path to a cache hit that
  does not go through the OpenNext handler. This is why the task's
  instruction not to reimplement cache-key/tag logic in `worker-entry.ts`
  rules out a bigger win here without a real deploy of a differently-built
  bundle.
- esbuild's own docs on `import()` without code splitting (wrangler bundles
  to a single output file, no splitting):
  https://esbuild.github.io/api/#splitting (fetched 2026-09-23): "Without
  code splitting enabled, an `import()` expression becomes
  `Promise.resolve().then(() => require())` instead ... the imported code is
  included in the same bundle instead of being split off into a separate
  file." So a dynamic `import()` of `open-next-worker` cannot shrink the
  upload (confirmed in §4: upload went up slightly, not down), but it does
  move the `require()` — and therefore the module's top-level execution —
  out of the synchronous top-level evaluation esbuild runs at load, to
  whichever request first evaluates that line.
- Secrets on `env`: https://developers.cloudflare.com/workers/configuration/secrets/
  (fetched 2026-09-23): "Secrets can be accessed from Workers as you would
  any other environment variables ... through the `env` parameter" —
  confirmed this also holds for `wrangler dev`'s local `.dev.vars` secrets,
  by reading the printed binding table (`env.REVALIDATE_SECRET ("(hidden)")
  Environment Variable local`) during every preview run in this task.
  `cloudflare-env.d.ts` (generated, not in this task's write scope) does not
  declare `REVALIDATE_SECRET` because it is a Worker secret, not a
  `wrangler.jsonc` `vars` entry — `worker-entry.ts` widens the type locally
  (`WorkerEnv = CloudflareEnv & { REVALIDATE_SECRET?: string }`) rather than
  editing the generated file.

## 4. Change made

`worker-entry.ts`:
- `POST /api/revalidate` is now checked in this file, before
  `openNextWorker` is imported at all: unset `REVALIDATE_SECRET` -> 404;
  wrong/missing bearer -> 401, same JSON body shape as the route's own
  check. Uses `isAuthorizedRevalidateRequest` from `src/lib/revalidate.ts`
  (constant-time `secretsMatch` underneath) — not reimplemented.
  `src/app/api/revalidate/route.ts` is unchanged; its own check still runs
  for every request that reaches it, as defence in depth.
- `import openNextWorker from 'open-next-worker'` (static, top-level)
  replaced with `const openNextWorker = (await import('open-next-worker')).default`
  inside `fetch`, in the one fallthrough branch that still needs it. Every
  request this file answers itself — the `/admin` redirect and every
  `/api/*` refusal, including the two new `/api/revalidate` cases — now
  never triggers that `require()` at all.
- Import of `isAuthorizedRevalidateRequest` uses a relative path
  (`./src/lib/revalidate`), not the `@/*` tsconfig alias
  `src/app/api/revalidate/route.ts` uses: `vitest.config.ts` (out of this
  task's write scope) has no matching resolver, and the unit test below
  needs to import `worker-entry.ts` directly under vitest/Node resolution,
  which only understands relative paths without one.

`pnpm typecheck`: exit 0. `pnpm build:worker`: exit 0 (same warnings as
before — `typeof x === "null"` in a Next-internal chunk, `direct eval` in
OpenNext's own handler — both pre-existing, unrelated to this change).

**Total Upload: 29651.96 KiB / gzip: 6520.38 KiB** — **+31.69 KiB (+0.11%)**

### 5c. First real HTTP request to an already-started process, refused route

Two independent fresh-process runs, first request = `POST /api/revalidate`
with `Authorization: Bearer wrong` (`REVALIDATE_SECRET` set via `.dev.vars`):

  revalidate-401-after.cpuprofile: samples=9 idle=551.18ms program=0.00ms named-js=0.62ms  non-idle=0.62ms
  final-revalidate-401.cpuprofile: samples=8 idle=474.21ms program=39.59ms named-js=3.35ms  non-idle=42.94ms

Both returned `401` with body
`{"ok":false,"error":{"code":"UNAUTHORIZED","message":"Invalid or missing revalidate secret."}}`.
The two runs disagree sharply on `(program)` time (0.00 ms vs 39.59 ms) —
with only 8–9 samples on a shared, multi-container machine, a single sample
landing during an unrelated scheduler preemption swings the total by tens of
ms; this is noise, not signal, and is reported honestly rather than
picked to fit either direction.

**What is not noise, and is the actual finding:** in both runs, the *only*
named JS functions touched are `isAuthorizedRevalidateRequest`,
`__facade_invokeChain__` (wrangler's own middleware plumbing), and
`read`/`getReader` (draining the request body stream). Neither run touches
`routingHandler`, `cacheInterceptor`, `generateResult`, `mapD1Result`, or
any other function that appeared in every cache-HIT profile above. This was
checked directly, not inferred: full per-sample function lists for both
files are in this task's working set (not retained past this evidence file;
regenerable from `worker-entry.ts` + the protocol in §1). The categorical
absence of every OpenNext/cache/D1 function — not the noisy millisecond
totals — is the evidence that the dynamic import achieves what it was
meant to for this route class.

`GET /admin` (redirect) was spot-checked the same way on the same
never-warmed process right after the revalidate-401 request and returned
`308` with no `x-opennext-cache` header, consistent with also skipping the
OpenNext handler, but not independently profiled as its own fresh-process
first request (budget; the mechanism is identical to the revalidate case —
neither branch reaches the `import()` line).

## 8. What was verified vs. assumed

command and what it measures; secrets are readable on `env` at runtime even
though the generated type does not declare them; a dynamic `import()` does
not shrink a single-file esbuild bundle (upload went up, not down);
`/api/revalidate`'s early gate produces byte-identical 401/404 behaviour to
before, with the OpenNext handler categorically untouched; `pnpm check`,
`pnpm build:worker`, and the full e2e suite all pass against the final
build.

Assumed / not independently re-verified here: the hosted 17–46 ms
fresh-isolate and 2–5 ms warm-isolate numbers and the 118 ms hosted
`/api/revalidate` cost are I20/I21's own hosted measurements, taken as given
per this task's brief ("no deploy, no hosted calls") — not reproduced or
re-checked against a live Worker in this task. Whether the `/api/revalidate`
fix reduces that 118 ms hosted figure, and by how much, is not verified —
only the local, relative, same-hardware comparison in §5c is.

## 9. Remaining risk / recommendation (I21 options 1–3)

Option 1 (profile and cut what is measurable, $0) was followed as far as
this task's own guardrail allows (no cache-key/tag reimplementation in
`worker-entry.ts`, no deploy). It produced one real, verified, narrow win:
an isolate whose first request is `/admin`, or any refused `/api/*` path
including an unauthenticated `POST /api/revalidate`, no longer touches the
~29 MB OpenNext bundle at all. For a low-traffic public site that also
receives scanner/bot traffic on `/admin` and `/api/*`, this removes real,
previously-wasted CPU on isolates that would otherwise have paid for a full
Next.js/Payload module load just to return a 404 or 308.

It does **not** reduce CPU for the traffic I21 actually flagged as the
common case: an ordinary visitor whose first request to a fresh isolate is
a real page. §5b's own measurement makes this concrete — the true first-page
cost, now fully inside the profiled window instead of partly hidden before
it, is *higher* than §2b's original (incomplete) number, not lower. The
gap I21 describes between a 2–5 ms warm cache hit and a 17–46 ms
fresh-isolate cache hit is still there; this task's change does not touch
it, and could not without either reimplementing OpenNext's own cache
lookup outside the handler (explicitly out of scope) or reducing what that
handler has to evaluate in the first place (I20's duplicate-Payload-compile
lead, not pursued here).

Recommendation: keep this change (it is a real, low-risk, $0 win with a
measured +0.11% upload cost), but do not treat I21 as closed by it. The
remaining gap is a page-serving-isolate problem, not an
`/api/revalidate`-shaped problem. Of I21's three options, this task's
evidence does not newly favour option 2 or 3 over option 1 — it narrows what
"option 1" can still mean: the next concrete, measurable step under option 1
is bundle size (I20's flagged duplicate-compile lead), not further
`worker-entry.ts` routing changes, since every remaining `worker-entry.ts`
branch that reaches a real page already has to load the full handler by
design. Whether that is worth the effort against just accepting option 3
(Workers Paid, $5/month, breaks the owner's $0 window) is the owner's call,
not resolved here.

## R2.3 Experiment: exclude Payload's admin/API routes from only the Worker build

Mechanism, verified from installed Next 16.3.5 source before writing any
code (not assumed): `node_modules/next/dist/build/route-discovery.js`'s
`createPagesMapping` is called with `pagesType: PAGE_TYPES.APP` and the
configured `pageExtensions` for the app directory scan, and
`node_modules/next/dist/server/lib/find-page-file.js`'s
`createValidFileMatcher(pageExtensions, appDirPath)` builds its `page`/
`layout`/`route`/`not-found` regexes directly from that extension list
(matched against the full relative path regardless of nesting depth). The
official docs
(https://nextjs.org/docs/app/api-reference/config/next-config-js/pageExtensions,
version 16.3.5, fetched 2026-09-23) describe this option only in terms of
the Pages Router, which is stale/incomplete relative to the source -- the
source is what this change relies on, and it was confirmed empirically too
(below).

Changed:
- `src/app/(payload)/layout.tsx` -> `layout.admin.tsx`
- `src/app/(payload)/admin/[[...segments]]/page.tsx` -> `page.admin.tsx`
- `src/app/(payload)/admin/[[...segments]]/not-found.tsx` -> `not-found.admin.tsx`
- `src/app/(payload)/api/[...slug]/route.ts` -> `route.admin.ts`
- `src/app/(payload)/api/graphql/route.ts` -> `route.admin.ts`
- `src/app/(payload)/api/graphql-playground/route.ts` -> `route.admin.ts`
- `src/app/(payload)/admin/importMap.js` left unchanged, as instructed --
  none of the renamed files' relative imports of it changed, since only the
  leaf filename changed, not the directory.
- `next.config.ts`: added a `pageExtensions` entry, base extensions
  (tsx/ts/jsx/js) restated plus `admin.tsx`/`admin.ts`, conditioned on
  `process.env.WORKER_BUILD === '1'` to drop the `admin.*` pair (setting
  `pageExtensions` replaces Next's default list rather than merging with it
  -- confirmed from `node_modules/next/dist/server/config-shared.js`'s own
  default).
- `package.json`: `"build:worker": "WORKER_BUILD=1 opennextjs-cloudflare build"`.

Proof the mechanism works, both directions:

  $ PAYLOAD_SECRET=throwaway-build-secret pnpm build        (WORKER_BUILD unset)
  Route (app): /, /_not-found, /admin/[[...segments]], /api/[...slug],
    /api/graphql, /api/graphql-playground, /api/health, /api/revalidate,
    /probe/[id]            <- unchanged, all 9 routes present

  $ PAYLOAD_SECRET=throwaway-build-secret pnpm build:worker  (WORKER_BUILD=1)
  Route (app): /, /_not-found, /api/health, /api/revalidate, /probe/[id]
    <- admin + all 4 Payload API routes gone, exactly as intended

  Also: the two esbuild warnings present in every round-1 build
  ("direct eval", `typeof x === "null"`) are gone from this build -- both
  traced (round 1, section 3) to code paths only reachable through the
  admin/GraphQL routes.

Node target still works (Docker-equivalent, no Worker code):

  $ PAYLOAD_SECRET=throwaway-build-secret pnpm build; node .next/standalone/server.js
  GET /admin/login  -> 200, 50617-byte body (the real rendered login page)
  GET /api/users/me -> 200, {"user":null,"message":"..."} (Payload's own
                        REST response, not a 404)

Measurements, same protocol as round 1 (section 1):

`npx wrangler deploy --dry-run`:
  admin/API included (reverted baseline): Total Upload: 29621.85 KiB / gzip: 6515.00 KiB
  admin/API excluded:                     Total Upload: 13086.05 KiB / gzip: 2760.35 KiB
  -16535.80 KiB, -55.8%

`wrangler check startup`, 3 runs each build, back to back, same container:
  admin/API included: Active 40.1, 41.1, 40.1 ms  (avg 40.6 ms)
  admin/API excluded: Active 40.1, 38.5, 41.1 ms  (avg 39.9 ms)
  Ranges overlap almost completely. At this tool's own resolution (~29-31
  samples over a ~270-530 ms window, ~15-17 ms/sample) there is no
  measurable difference between a 29.6 MiB and a 13.1 MiB bundle's
  global-scope evaluation cost. This is a real, somewhat counter-intuitive
  finding, not a tooling failure: V8 lazily parses/compiles function bodies,

on this shared container (round 1's own "warm" second-request sample swung

"smaller bundle -> faster first request" claim here, and the direction is,
if anything, not favourable.

## R2.4 Decision: reverted

Per the instruction ("keep the change only if it measurably reduces startup
or first-request CPU"): it does not. `wrangler check startup`'s repeated,
back-to-back samples overlap between the two builds; the first-request CPU
samples show no consistent direction and are, on the limited data available,
slightly worse rather than better. The 55.8% smaller upload is real and
would matter for deploy bandwidth/time and for headroom against the
platform's separate 1-second Worker-startup wall-clock limit, but that is
not what this task's keep/revert criterion was measuring, and this task does
not claim it as a CPU win.

Reverted: `git mv` every renamed file back to its original name,
`next.config.ts`'s `pageExtensions` addition removed, `package.json`'s
`build:worker` script restored to `opennextjs-cloudflare build`. Confirmed
byte-identical to the pre-experiment state: `git diff next.config.ts
package.json` is empty after the revert. Final rebuild reproduced the exact
reverted baseline: `Total Upload: 29621.85 KiB / gzip: 6515.00 KiB`.
`pnpm check`: exit 0 (27/27 unit tests). Final e2e run against this exact
build: 6/6 passed.

The dead-code finding (R2.2/R2.3) is still worth recording for whoever picks
up bundle-size work next: excluding Payload's admin/API route files removes
about half the bundle by size, but neither local CPU measurement available
here shows that size difference turning into a CPU difference -- so the
already-flagged duplicate-Payload-compile chunks (I20, R2.2) are a stronger
lead for a future CPU-focused attempt than route-file exclusion is, if one
is ever made.
