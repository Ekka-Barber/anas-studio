ROOT CAUSE (confirmed by reading source, not assumed):
  Any import of @payload-config triggers buildConfig(), which processes every
  collection with `upload: {...}` (RuntimeProbeMedia) and unconditionally
  registers Payload's own default upload REST endpoints
  (payload/dist/uploads/endpoints/getFile.js,
  payload/dist/uploads/checkFileRestrictions.js) regardless of the custom
  storage-r2 adapter. Those files statically import fileTypeFromFile from
  file-type's edge-safe core.js export, which does not provide that
  (Node-fs-only) function. Next.js's own bundler (Turbopack, used by the
  successful `next build` above) tolerates the unresolved named export;
  wrangler's esbuild pass over worker-entry.ts (a separate, second bundling
  pass — worker-entry.ts is wrangler's own "main" entry, not part of the
  Next.js app graph) does not, and errors hard. This is not specific to my
  code's logic: any module that imports @payload-config from outside the
  Next.js/OpenNext build graph hits this, because RuntimeProbeMedia declares
  `upload: {...}` at all.

  Precedent for this exact class of problem already exists in the repo:
  next.config.ts's turbopack.resolveAlias aliases drizzle-kit/api to a Node
  builtin for an analogous esbuild/Turbopack resolution mismatch. The
  equivalent fix here would be a wrangler.jsonc build alias for 'file-type' (or
  disabling Payload's default upload endpoints), which are, respectively, a
  shared build manifest and a product-behavior change — both outside this
  package's write scope for this task.
