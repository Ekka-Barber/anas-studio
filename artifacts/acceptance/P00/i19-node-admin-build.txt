### Fix 1: autoRun never starts after a reboot until someone opens a route

`src/lib/payload.ts`'s `getPayloadClient()` now calls
`getPayload({ config, cron: isNodeRuntimeTarget() })` (was: no `cron` key at
all, i.e. always falsy). `/api/health` is the only caller that goes through
this helper without `@payloadcms/next`'s own `initReq.js` (which always
passes `cron: true`), so it was the one route that could run forever without
ever starting Payload's `autoRun` timer. Worker target unaffected:
`isNodeRuntimeTarget()` is false there, `cron: false`, identical to before.

Added a Dockerfile `HEALTHCHECK` (interval 60s, timeout 5s, start-period 30s,
retries 3) that polls `/api/health` with `node -e 'fetch(...)'` (the slim
image has no curl) — so after `--restart unless-stopped` brings the container
back up with nobody visiting the admin, the healthcheck itself is what makes
the first `/api/health` request happen, which is what starts the cron timer.

**Bug found and fixed while proving this**, before the official run: Docker
sets `HOSTNAME` to the container ID for every container by default (confirmed
via `docker exec ... env` and `/etc/hosts`, which mapped the container ID to
the container's bridge IP, not `127.0.0.1`). Next's standalone server does
`process.env.HOSTNAME || '0.0.0.0'` (`next/dist/build/utils.js`), so without
an override it bound only to the container's own bridge IP. Host-published
port access still worked (Docker's port DNAT targets the bridge IP directly —
confirmed, round 1's `/api/health`/`/admin/login`/login proofs all used
published-port access and all passed), but the in-container `HEALTHCHECK`
connects over loopback and got `ECONNREFUSED 127.0.0.1:3000` on every attempt
(reproduced manually via `docker exec <container> node -e "fetch(...)"`,
caught the `TypeError: fetch failed` / `ECONNREFUSED` directly). Fixed with
`ENV HOSTNAME=0.0.0.0` in the runtime stage, verified with a disposable
diagnostic container before the official run (`STATUS 200`, exit 0).

**Official proof run**, container `p00-admin-proof`, started
`2026-09-23T03:01:12.165633602Z`. No admin or REST request was made by
anyone (owner-equivalent) between start and the first successful
healthcheck.

  $ docker inspect --format '{{json .State.Health}}' p00-admin-proof
  (at 03:16:01Z) {"Status":"healthy","FailingStreak":0,
    "Log":[...5 entries, all ExitCode 0, 03:11:21Z through 03:15:22Z...]}

Direct database check (bypasses the app; not an HTTP request) confirmed the
job was queued, not yet run:

  $ docker exec p00-pg psql -U p00 -d p00_admin -c \
    "SELECT id, task_slug, queue, wait_until, completed_at, has_error, processing FROM cms.payload_jobs ORDER BY created_at DESC LIMIT 5;"
  f539571b-... | probeHeartbeat | default | 2026-09-23 03:30:00+00 | (empty) | f | f

**Finding, not a bug**: on a genuinely fresh database (no prior
`payload-jobs-stats` global), the first `autoRun` tick that reaches
`handleSchedules()` has no `lastScheduledRun` baseline, so
`checkQueueableTimeConstraints` (`payload/dist/queues/operations/handleSchedules/index.js`)
computes `nextRun(undefined)` — the *next* occurrence of the cron pattern
strictly after "now" — and queues the job with `waitUntil` set to that time,
one full cycle away, rather than running it immediately. `defaultAfterSchedule`
then records the real run time as the new baseline, so every tick after the
first is on-cadence (queue now, run now). Net effect: cold start costs up to
2x the cron interval (here, up to 30 minutes) before the first completed job
appears, not 1x. Read directly from the installed 3.90.1 source, not recalled.

**Requester's manual HTTP requests to this container, stated plainly:** yes.
`curl -sS http://127.0.0.1:3303/api/health` was run twice, as part of my own
verification scripts, at `2026-09-23T03:16:02.830Z` and
`2026-09-23T03:31:04.854Z` — both read-only GETs to the public, unauthenticated
health endpoint, no login, no admin route, no REST write. Both came *after*
the event each was checking had already happened on its own: the 03:16:02
request came after the healthcheck's own 5 logged successes (03:11:21Z-
03:15:22Z, all before my request) and after the direct DB query already
showed the job queued; the 03:31:04 request came after
`completed_at 2026-09-23 03:30:00.13+00` was already written to the database
(confirmed by direct DB query moments before the HTTP request, in the same
background script). Neither request could have caused cron registration or
the first job to run — both had already happened, independently, by the
time each request was made. The `docker exec p00-pg psql ...` calls query
the database directly and are not requests to the container.

**Independently confirmed by the orchestrator**, reading the same running
container over a longer window than this task waited: `p00-admin-proof`
logged "Running 1 jobs" at 03:30, 03:45 and 04:00 UTC — exactly the steady-
state, on-cadence behaviour predicted above once the cold-start baseline was
set — and `/api/health` reported `lastCompletedAt: 2026-09-23T04:00:00.081Z`,
`healthy`.
